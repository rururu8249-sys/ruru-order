# B. 교환·환불 장부 — 조사·설계 보고 (코드 미작성)

> 2026-09-26 조사. 이 문서 작성 시점에 코드/DB는 전혀 건드리지 않음. 착수는 사장님 확인 후.

## 1) 지금 교환·환불이 저장되는 곳 (실제 코드 기준)

교환·반품 1건이 저장되는 곳은 **세 군데로 흩어져** 있음. 진입점은 `app/api/admin-live/order-return/route.ts`:

| 저장처 | 내용 | 비고 |
|---|---|---|
| **`orders.return_*`** | `return_status`(예 "반품(환불)"/"반품(교환)"), `return_reason`(대상상품+세부), `return_updated_at` — 그룹 전체 행에 동일 기록 | `orders_return_columns.sql`(ADD COLUMN only). **`return_amount` 컬럼은 있지만 route가 안 채움**(현재 미사용). 명시적으로 "정산/입금/재고/포인트 계산 어디에도 안 씀" |
| **`admin_tasks`** (=고객이슈 탭) | `task_type`=exchange/refund/general, `source="order_return_flow"`, `raw_payload.items`(상품 id·색·사이즈·수량), `status`=open | 자동 등록. `isReturnFlowIssue`=`source==="order_return_flow"`로 판정 |
| **`customer_point_ledger`** | 환불(refund)일 때만 적립 포인트 회수: `change_type="cancel"`, `amount=-회수액`, `created_by="order_return_flow"`, `related_order_id=groupId` | **이중 회수 방지**: 같은 `related_order_id`+`created_by`가 있으면 스킵 |

**「자동」 반품 흐름 단계별로 쓰는 것:**
1. `orders` 업데이트(return_*) → 2. `admin_tasks` insert(고객이슈) → 3. refund면 포인트 회수 ledger insert(안분 비율·잔액 마이너스 허용). 되돌리기는 `order-return/undo/route.ts` — `change_type="adjust"`로 재지급 + admin_task 삭제, 손으로 이미 지급한 기록이 있으면 경고.

→ **단계(접수/회수/도착/완료 등)라는 개념 자체가 지금은 없음.** `admin_tasks.status`(open/done/deleted)만 있음. **환불 계좌(은행·계좌번호·예금주) 저장 컬럼은 어디에도 없음**(grep 0건) → 장부의 계좌·다단계·조정줄은 전부 신규 저장이 필요.

## 2) 저장 방식 후보 (DB는 ADD COLUMN only 원칙)

**후보 A — `admin_tasks`에 ADD COLUMN** (`refund_stage`, `refund_amount`, `refund_method`, `refund_adjustments`(jsonb), `refund_bank`/`refund_account`/`refund_holder`, `refund_done_at`)
- 장점: 기존 이슈 1건 = 장부 1건, `source="order_return_flow"`로 이미 연결됨. 마이그레이션 거의 불필요.
- 단점: admin_tasks는 «범용 할 일» 테이블 — 환불 전용 스키마·계좌 PII가 섞여 지저분. 계좌 보호(뒷4자리·만료삭제)를 범용 테이블에 얹기 껄끄러움. 단계 enum·조정줄 확장성 낮음.

**후보 B — 신규 테이블 `refund_ledger`** (order_group_id·kakao_id/customer_id·stage·type·reason·product_snapshot(jsonb)·amount_base·adjustments(jsonb)·amount_final·method·bank/account/holder·done_at·created_at)
- 장점: 스키마 깔끔, **전용 RLS(anon 전면 차단)**, 단계 탭·조정줄·합계·이체목록복사 전부 자연스럽게. 계좌 마스킹/만료삭제 로직을 이 테이블에만 적용.
- 단점: **신규 테이블 생성은 "ADD COLUMN only" 원칙을 넘어섬** → 사장님 명시 승인 필요. (단, 기존 테이블을 안 건드리므로 ADD COLUMN보다 오히려 회귀 위험은 낮음.) 기존 고객이슈와의 연결(마이그레이션) 작업 필요.

**추천: 후보 B**(신규 `refund_ledger`) + 계좌는 이 테이블에만. 범용 admin_tasks에 계좌 PII를 얹지 않는 게 안전. 단 «신규 테이블» 승인만 주시면 됨.

## 3) 돈 위험 — 이중 처리 안 되는 구조인가  ★2026-09-26 정정

- **[정정] 이전 보고의 "포인트 환불은 order-return 엔드포인트 호출"은 틀림.** `order-return`의 포인트 처리는 **«적립 포인트 회수(차감)»**이고, 장부의 **«포인트로 환불»은 «지급»**이라 방향이 정반대. 두 가지를 엮으면 안 됨.
- **1단계 원칙: 장부는 포인트를 절대 움직이지 않음(기록만).** `order-return`, `order-return/undo`, `customer-points` 등 포인트·주문 라우트와 RPC는 수정 금지. 포인트 방법 환불은 3단계에서 연결하고, 지금은 «포인트 메뉴에서 직접 지급 후 장부에 기록»만.
- **장부는 기록 전용**: 실제 현금 이체는 은행앱(시스템이 금액을 옮기지 않음) → 장부는 "이체했어요 체크 + 이체일(transferred_at)·완료일(done_at) 기록"만. 이중 이체는 사람이 체크로 관리.

## 4) 계좌번호 보호 설계

- **RLS**: `refund_ledger`는 `customer_point_balances`와 동일하게 **anon 정책 없이 RLS on** → 브라우저에서 직접 못 읽음.
- **서버 라우트만**: 읽기/쓰기 모두 `verifyAdminSessionFromRequest`+service_role 라우트(예 `/api/admin-live/refund-ledger`)로만. (회원 목록 batch 라우트와 같은 패턴.)
- **목록엔 뒷4자리만**: 라우트가 목록 응답에 `account_last4`만 내려주고, 전체 계좌번호는 «환불 처리 창을 열 때» 별도 요청으로만.
- **만료 가림/삭제**: `done_at` 후 N일(예 30일) 지나면 계좌번호를 마스킹 또는 NULL로(cron 또는 조회 시 지연 마스킹). 예금주·은행은 남기고 계좌번호만 지우는 방식 권장.

## 5) 기존 고객이슈 → 장부 이전

- **자동 변환 가능**: `source="order_return_flow"`인 건(구조화됨) → stage 자동 추정(status open→「접수」, done→「완료」, deleted→「취소」), type=task_type(exchange/refund), amount_base=orders 금액, product_snapshot=raw_payload.items. 포인트 회수 ledger가 있으면 「처리 결과」에 반영.
- **사람이 봐야 할 범위**: `source`가 없고 task_type만 exchange/refund/return인 «손입력» 건(자유 텍스트라 금액·계좌 불명), 그리고 **계좌번호는 원래 수집한 적이 없어 전부 공란** → 실제 이체할 때 사장님이 입력. 진상/구매 등 교환·환불 아닌 유형은 이전 대상 아님.

**확인 요청**: (a) 저장 방식은 **후보 B(신규 `refund_ledger` 테이블)**로 갈지, admin_tasks ADD COLUMN(후보 A)로 최소화할지. (b) 신규 테이블이면 「ADD COLUMN only」 예외를 승인하는 것으로 이해하면 되는지. 확인 후 B 코드/SQL 작성 착수.
