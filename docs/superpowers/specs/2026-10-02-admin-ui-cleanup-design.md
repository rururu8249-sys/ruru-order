# 관리자 화면 정리 설계 — 2026-10-02

## 목적과 범위
사용자는 관리자 기능이 누적되어 메뉴와 설명이 흩어지고 목록 공간이 줄어든 문제를 해결하고자 한다. 가끔 사용하는 기능은 보존한다. 입금내역을 입금매칭처럼 오른쪽에서 열고, 미사용 트렌드 추천은 기본 노출에서 제외한다.
이 문서는 공통 메뉴·설정 탐색·입금내역 패널을 우선 정리하는 설계다. 개별 업무의 미확인 동작을 추측하여 삭제하거나 변경하지 않는다. 고객 주문서와 금융·배송 판정은 범위 밖이다.
사용자는 이전에 제시한 정리 방향에 대해 “알아서 잘 만들어줘”라고 답했다. 이 문서는 그 방향을 구현 가능한 기준으로 구체화한 검토본이며, 아직 구현·배포하지 않았다.

## 실제 운영 순서 (사용자 설명 반영)
사용자는 방송 중과 종료 직후 실시간 주문서 → 상품 → 입금 → 고객 → 물건챙김 순으로 많이 확인한다고 설명했다. 이는 사용자 제공 운영 정보이며, 클릭 로그로 측정한 빈도나 순위는 아니다.
공통 작업 바로가기는 이 순서로 둔다. 기존 큰 메뉴 5개와 설정 접근은 유지하되 작업 바로가기를 또 하나의 큰 설명 카드로 만들지 않는다. 짧은 한 줄 버튼으로 구성한다.
- 실시간 주문서: 기존 주문 목록으로 이동한다.
- 상품: 기존 상품 관리로 이동하며 이전 상품 탭과 검색을 유지한다.
- 입금: 주문 화면을 바탕으로 입금내역 우측 패널을 연다. 기존 입금매칭 진입은 별도로 유지한다.
- 고객: 기존 고객 화면으로 이동한다. 확인 가능한 기존 상태 보존 경로를 사용한다.
- 물건챙김: 기존 물건챙기기 기능으로 직접 연결한다. 새 챙김 상태나 별도 체크리스트를 만들지 않는다.
현재 물건챙기기 버튼은 LiveOrderTable.tsx 내부에서 pickingScopeOrders를 대상으로 기존 모달을 연다. 직접 바로가기 구현에서도 같은 범위 계산·기존 모달·기존 저장 경로를 재사용한다. 다른 화면에서 열 때도 대상 방송/쇼핑몰·기간이 명확히 표시되어야 하며, 현재 방송이라고 추측하거나 전체 주문으로 임의 확장하지 않는다.
방송 종료 직후 방송 범위가 사라지거나 다른 방송으로 바뀌는지 반드시 확인한다. 종료 여부만으로 작업 범위를 리셋하지 않는다. 취소·제외 주문 및 결제 상태 필터는 기존 검증된 기준을 유지한다.
다섯 작업을 순서대로 왕복하는 검수 시나리오를 추가한다. 주문 범위, 상품 검색, 입금 목록과 챙김 상태가 서로 다른 데이터로 바뀌거나 초기화되는지 확인한다.
전체 메뉴 검수 범위는 축소하지 않는다. 이 순서는 배치와 우선 검수 순서에 반영하되 나머지 기능을 삭제하는 근거로 사용하지 않는다.

## 전체 관리자 검수 범위 (사용자 추가 요청 반영)
앞서 명시한 메뉴뿐 아니라 관리자에서 도달 가능한 모든 화면을 검수한다. 코드의 파일 존재만으로 실제 사용 가능한 메뉴라고 단정하지 않는다. 메뉴 정의→실제 진입 버튼→표시 화면→닫기/돌아오기→데이터·입력 유지까지 연결하여 확인한다.

| 업무 | 반드시 확인할 화면과 기능 |
| --- | --- |
| 방송 | 방송 콘솔, 시작·종료 화면, 채팅주문 대기열, 방송 기록·리포트, 접이식 방송·채팅 레일 |
| 주문·입금 | 주문 목록·필터·정렬, 주문 상세, 입금매칭, 입금내역·입금 상세, 카드결제 안내, 물건챙기기(상품별·고객별), 송장 출력·출력 해제, 일괄 작업, 정산과 그 내부 연결 기능 |
| 상품 | 방송 상품, 쇼핑몰 진열, 전체 상품, 판매 기록, 상품 등록·수정, 브랜드 그룹·세부상품 편집, 상품 담기·복사, 엑셀 등록, 재고·옵션, 방송·고정·채팅 동작 |
| 고객 | 회원 목록·상세·수정, 고객이슈와 교환·환불 진입, 단골, 계정 연결 요청, 차단, 포인트, 접속 기록 |
| 공지·쪽지 | 손님 화면 공지, 접속 팝업·상단 공지, 구매동의, 공지사항 목록·등록·고정·순서, 쪽지 보내기·보낸 쪽지 |
| 이벤트 | 현재 주문·입금에 있는 이벤트 화면 및 내부 게임·미션 메뉴. 실제 진입 가능한 종류를 구현 파일과 UI에서 대조 |
| 설정 | 기존 12개 항목 전부와 시스템 점검 상세. 각 항목의 저장 버튼, 경고, 실패 안내, 외부 연동 동작 |
| 공통 | 모든 화면의 제목·탭·검색·필터·정렬·목록·페이지 이동·더보기·팝업·패널, 라이트/다크, 문의·카드결제 바로가기, 접속 현황, 모바일 메뉴, 로그아웃 |

이 표는 코드 탐색으로 확인한 검수 대상이며, 전 항목의 브라우저 검수가 끝났다는 뜻이 아니다.
각 항목은 ‘코드 진입 확인 / 화면 확인 / 개선 필요 / 개선 검증 / 변경 불필요 / 접근 제한’으로 기록한다. 파일이 있지만 진입 경로가 없으면 별도로 표시한다. 접근 제한·빈 데이터·확인 불가를 정상 통과로 처리하지 않는다.
모든 메뉴를 확인하기 전 “관리자 전체 최적화 완료”라고 보고하지 않는다. 변경 불필요한 화면에도 판단 근거를 남긴다.
전체 확인 결과를 우선순위별로 설계에 반영한 뒤 구현 범위를 확정한다. 모든 화면을 확인한다는 것은 모든 화면을 무조건 재작성한다는 뜻이 아니다.

## 확인된 현재 구조
- adminLiveMenu.ts: 큰 메뉴 5개, 하위 화면 키 13개. URL의 panel 키와 기존 이동 호출이 연결되어 있다.
- AdminLiveSettingsPanel.tsx: 12개 설정 탭. payment/point/order는 공통 저장을 쓰며, shop 등은 자체 저장 방식이 있다.
- AdminLiveDashboard.tsx: payments는 전체 화면, 주문상세/매칭은 최대 420px 우측 단일 패널이다.
- AdminLivePaymentPanel.tsx 및 payment-ledger/PaymentMatchPanel.tsx: 기존 입금내역은 검색, 기간, 상태, 정렬, 요약, 상세와 새로고침을 제공한다. 부모 목록과 자체 조회가 함께 존재한다. 패널 이동 시 이 경로를 검증 없이 새 조회 구조로 교체하지 않는다.
- AdminLiveNoticePanel.tsx: 공지는 설정과 같은 키를 두 곳에서 저장하던 덮어쓰기 위험 때문에 분리되어 있다. 화면 위치 정리와 저장 주체 복제는 별개다.
- 트렌드 미사용은 사용자의 명시적 운영 정보다. 다른 기능의 사용 빈도는 측정되지 않았다.

## 선택한 방식
버튼만 축소하면 기능의 위치 문제를 해결하지 못한다. 전체 기능 삭제·전면 재작성은 사용자가 가끔 쓰는 기능과 기존 운영 동작을 훼손할 위험이 있다.
따라서 기존 화면·데이터 계약을 유지하고 공통 탐색과 레이아웃을 정리한다. 기능 제거가 아니라 기본 노출과 보조 노출을 구분한다.

## 메뉴와 설정
큰 메뉴 5개(방송, 주문·입금, 상품, 고객, 설정)는 유지한다. 기존 주소와 하위 키도 유지한다. 이벤트를 포함한 기존 하위 기능을 임의로 다른 업무 영역으로 이동하지 않는다.
사이드바의 반복 설명은 기본 화면에서 줄이고 메뉴 이름과 예외 건수는 남긴다. 실시간 접속·문의·카드결제 접근은 보존한다.
설정의 12개 항목을 다음 묶음으로 표시한다. 묶음은 탐색을 위한 것이고 저장 범위는 기존과 같다.

| 묶음 | 기존 항목 |
| --- | --- |
| 결제·배송 | 상점 정보의 계좌·페이스터 바로가기, 결제·배송, 합배송 |
| 주문·상품 안내 | 주문서 표시, 상품사진 문구, 기존 공지 화면으로의 바로가기 |
| 고객 혜택 | 포인트 적립 |
| 방송·알림 | 방송 화면, 알림음, 유튜브 알림, 텔레그램 알림 |
| 상점·보안 | 상점 정보, 관리자 보안, 시스템 점검 바로가기 |
| 추가 기능(기본 접힘) | 트렌드 추천 |

계좌와 페이스터 바로가기는 기존 상점 정보 편집 화면의 해당 구역으로 이동한다. 입력 폼 또는 저장 API를 복제하지 않는다. 공지도 기존 편집 화면으로 이동한다.
설정 내 항목명 검색을 제공한다. 검색 결과에서 기존 편집 항목을 연다. 별도 서버 검색이나 신규 DB 필드는 만들지 않는다.
열린 설정 탭과 미저장 입력을 보조 메뉴 펼침만으로 초기화하지 않는다. 실제 탭 전환 시 미저장 값이 유실되는지 먼저 확인하고, 유실되는 화면에는 전환 전 저장/버리기/계속 편집 선택을 제공한다. 저장을 자동으로 실행하지 않는다.
트렌드 데이터, 연동 설정, 접근 권한은 변경하지 않는다.

## 공통 레이아웃
- 제목과 주요 동작은 짧은 상단 한 줄에 배치한다.
- 목록 검색·필터·정렬은 목록 바로 위에 모은다. 실제 업무에 필요한 필터는 없애지 않는다.
- 반복 설명은 도움말/더보기에 두되 금융·삭제·저장 경고는 숨기지 않는다.
- 주 동작, 보조 동작, 위험 동작의 색과 위치를 일관되게 구분한다. 빨강은 오류·삭제에 쓰고 모든 버튼을 강조하지 않는다.
- 데스크톱 일반 버튼은 36~40px 높이를 목표로 하고 터치 환경은 44px 이상 클릭 영역을 확보한다. 수치는 설계 목표이며 현재 측정치가 아니다.
- 텍스트만 축소해 목록 공간을 확보하지 않는다. 중복 여백과 설명 카드부터 줄인다.
- 1440×900, 1280×800, 390×844에서 잘림, 겹침, 가로 스크롤과 주요 동작 접근을 확인한다.
- 공통 틀 변경이 미치는 모든 하위 화면을 검수한다. 미확인 개별 폼을 일괄 CSS로 강제 축소하지 않는다.

## 입금내역 패널
주문 화면의 입금내역 동작은 주문 목록을 유지한 채 오른쪽 패널을 연다. 기존 panel=payments 직접 주소는 주문 화면을 바탕으로 입금내역 패널을 열도록 호환 처리한다.
패널 상태는 닫힘/주문상세/입금매칭/입금내역 중 하나다. 서로 겹쳐 열리지 않는다. 기존 매칭에서 주문상세로 이동하는 흐름은 보존한다.
데스크톱 패널은 입금 목록에 맞춰 최대 560px 폭을 목표로 한다. 작은 화면은 전체 폭을 사용한다. 목록과 상세는 패널 내부에서 전환하며 모달을 중첩하지 않는다.
상단: 입금내역 제목, 닫기, 새로고침. 검색과 상태 필터는 바로 아래. 날짜 범위는 압축하되 현재 적용 기간이 항상 보이게 한다.
본문: 입금자명, 금액, 입금 시각, 기존 판정 상태. 행 선택 시 같은 패널에 기존 연결 주문 정보를 표시한다. 상세의 “목록으로”는 검색·기간·정렬·스크롤을 유지한다.
입금 상태를 추측하여 새 이름으로 판정하지 않는다. 기존 레이블과 표시 값을 그대로 사용한다. 표시된 합계는 필터된 범위라는 점을 명확히 한다.
패널을 닫아도 주문표 필터, 검색, 선택 기준과 스크롤을 초기화하지 않는다. 배경은 기존 우측 패널처럼 조작을 잠그고 닫으면 호출 버튼으로 포커스를 돌린다. Esc 닫기와 키보드 탐색을 지원한다.
조회 실패는 빈 목록과 구분한다. 최신화 실패 시 마지막 확인 목록과 오류를 함께 표시하며 “최신 데이터”라고 표시하지 않는다. 중복 새로고침과 늦은 응답으로 화면이 덮이는지 테스트한다.
이 개편은 조회·표시를 정리하는 작업이다. 자동매칭, 수동 연결, 금액 계산, Bankda 수집 정책, 주문 결제 상태 API는 변경하지 않는다. 숨김/닫힘 시 불필요한 타이머가 계속 작동하지 않는지 확인한다.

## 검증 및 완료 조건
1. 기존 13개 하위 화면의 진입 경로가 남고 직접 주소가 호환된다.
2. 트렌드는 기본 접힘 추가 기능에서 찾을 수 있으며 데이터는 그대로다.
3. 계좌·공지 등 바로가기가 기존 저장 주체로 연결되고 중복 편집 폼이 없다.
4. 주문표에서 입금내역 열기→검색→기간 변경→상세→목록→닫기 후 주문표 상태가 유지된다.
5. 주문상세/매칭/입금내역 전환마다 패널이 하나만 열린다.
6. 빈 목록, 로딩, 실패, 느린 응답, 연속 새로고침, 긴 이름·금액·다수 건을 테스트 데이터로 검증한다.
7. 금융/배송/주문 상태 관련 기존 테스트, 타입 검사, 빌드가 통과한다.
8. 동일 화면 크기·동일 데이터로 전후 목록 표시 행 수와 상단 사용 높이를 측정해 기록한다. 측정 없이 공간 확보 완료라고 주장하지 않는다.
9. 실제 배포 후 읽기 전용으로 동선과 화면을 확인한다. 고객 주문 제출·입금 연결·방송 종료를 테스트 목적으로 실행하지 않는다.
10. 실제 사용자의 오조작·작업 속도는 추가 사용 검증 대상이다. 기술 검수 통과만으로 “완벽/최선/버그 없음”이라 주장하지 않는다.

## 적용 순서와 복구
입금내역 패널 → 설정 탐색 정리 → 공통 메뉴·밀도 정리 순으로 분리한다. 각 단계마다 기존 기능 회귀 검증을 진행한다.
DB 마이그레이션, 운영 데이터 삭제, 새 의존성 설치 없이 구현한다. 코드 변경은 단계별로 되돌릴 수 있게 분리한다. 문제가 생기면 화면 변경을 되돌리고 기존 서버 및 운영 데이터는 유지한다.
