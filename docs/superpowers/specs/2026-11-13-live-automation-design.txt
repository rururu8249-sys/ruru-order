루루동이 실시간 주문·채팅·시청자 통합 설계서
2026년 11월 13일 | 설계안 v1.3 | 기존 ON/OFF UI·인물별 말투·닉네임별 주문서·자원 중지 반영

목적
유튜브에서 실제 방송이 진행되는 동안, 아직 고객 이용이 적은 사이트의 방송 시청·접속 수·채팅·장바구니·주문서·관리자 주문 목록이 실제 운영 과정대로 연결되는지 확인한다. 접속 숫자나 주문 성공 화면만 임의로 만들어 보여주지 않는다.

선택한 구조는 기존 회원 1개, 독립된 접속 세션 여러 개, 서버에서 실행하는 이용 시나리오, 소수의 실제 브라우저를 함께 사용하는 방식이다. 화면은 일반 운영 모습으로 보이게 하고, 생성한 데이터의 구분과 금전 보호는 서버 내부에서 유지한다.

이 문서는 최초 요청서 전체와 이후 대화에서 바뀐 표시·접속·부하 요구사항을 합친 설계다. 구현·배포·실제 실행 결과 보고서가 아니다. 문서 작성 과정에서 운영 계정·주문·설정·결제 정보는 변경하지 않았다.

읽는 순서
1~3장은 결정 사항과 현재 상태, 4~7장은 계정·접속·실행 구조, 8~12장은 주문·채팅·AI, 13~16장은 화면·운영·적용 순서, 17장은 검증표, 18~20장은 요구사항 대응·결과 보고·자료다.


1. 이번 대화에서 확정한 방향

1.1 최초 요청보다 최신 지시를 우선하는 부분
• 기존에는 공개 시청자 수에 생성한 접속을 제외하도록 요청했지만, 이제는 일반 회원 화면에서도 그 접속에 따라 숫자가 실제로 변하는 것을 확인한다.
• 기존에는 닉네임 앞에 (테스트), 주문자 옆에 [TEST], 공개 채팅에 AI 표시를 요구했지만, 이번 실사용 확인 실행 중에는 일반 화면과 실사용 확인용 관리자 채팅·주문 목록에 해당 접두어를 표시하지 않는다.
• 실제 저장 닉네임에는 원래부터 어떤 접두어도 붙이지 않는다. 내부 자동 생성 구분값은 제거하지 않는다.
• 일반 화면의 눈 숫자와 ‘사이트 N’ 표기, 상품 카드, 채팅 배치, 주문 목록의 기존 디자인을 유지한다.
• 회원 수만큼 브라우저를 계속 띄우지 않는다. 입장·유지·퇴장 요청 대부분은 서버가 보내고, 화면·영상·주문 버튼 검증에는 실제 브라우저를 소수 사용한다.

Gemini 예산에 대한 최신 수정: 제공자 주 모델 일일 500회와 사이트 자체 150회를 구분한다. 최초 문서의 고정 150회 유지 요구는 이후 사용자의 ‘무료 범위 안에서 필요한 AI를 최대한 활용’ 지시로 변경한다. 150회는 과거 설정으로 기록하고 새 설계의 고정 차단값으로 사용하지 않는다. 모든 실제 시도와 다른 AI 기능을 함께 계수하는 조건은 유지한다.

최신 추가 확정 사항
• 주문하는 닉네임마다 서로 다른 주문서 1~3건이다. 상품 종류나 수량의 1~3개를 뜻하지 않는다. 시청만 하는 인물은 주문서 0건이어도 된다.
• 상품 질문을 올렸다면 같은 닉네임으로 30초~2분 뒤 해당 상품을 포함해 제출한다. 전체 자동 제출은 계속 5~10분 간격으로 제한한다.
• 질문한 상품이 품절·삭제·판매중지라면 주문서 제출 요청 자체를 보내지 않는다. 다른 상품으로 몰래 대체하지 않는다.
• 남녀·30/40/50대의 다양한 가상 인물 설정과 각자의 어휘·문장 습관을 유지한다. 실제 회원의 나이·성별을 추정하는 기능은 만들지 않는다.
• 첨부한 기존 관리자 카드의 스위치와 ‘지금 테스트’를 유지한다. 원하는 때 켜서 반복하고 끄면 관련 예약·호출까지 멈춘다. 사이트 주문 본격 시작 전까지 이 조작을 반복할 수 있다.
• 공개 방송 화면에서 테스트 표식이 보이지 않는 요구와 관리자 전용 제어 문구는 구분한다. 관리자 설정의 ‘자동 테스트 주문/채팅/지금 테스트’는 유지한다.

1.2 그대로 유지하는 원칙
• 회원 임의 추가·삭제·통합 금지. 기존 자동 회원 1개 재사용.
• 시청자 수는 접속 기록을 집계한다. 채팅 횟수·주문 횟수를 인원에 더하지 않는다.
• 실제 장바구니와 주문 제출 경로를 사용하되 실제 결제 승인·입금 매칭·재고 차감·매출·정산·배송에는 영향을 주지 않는다.
• 모든 Gemini 기능은 중앙 호출 관리 시스템을 통과한다. 유료 전환, 결제 계정 연결, 추가 프로젝트·키로 한도 우회 금지.
• 자동 주문, 자동 채팅, 자동 접속은 독립적으로 제어한다. Gemini가 중단돼도 주문과 접속 기능은 계속 실행한다.
• 운영 화면에 복잡한 로그 페이지를 새로 만들지 않는다.

1.3 공개 화면과 내부 기록의 차이
실사용 확인 실행이 활성인 동안에는 눈 숫자에 유효한 실제 접속과 생성한 접속을 함께 표시한다. 예를 들어 운영자 관찰 접속 1개와 자동 접속 3개가 방송 화면을 열고 있으면 눈 숫자는 4다. 공개 화면에는 별도의 ‘테스트’ 문구를 붙이지 않는다.

이 숫자는 실제 사람 수 또는 유튜브 시청자 수를 인증하는 지표가 아니다. 사이트가 수신한 유효한 시청 접속의 수다. 유튜브 API가 돌려주는 동시 시청자 숫자는 별도 값으로 유지하며 여기에 더하지 않는다. 분석·마케팅·방송 요약의 실제 고객 통계에는 자동 접속을 제외한다.

관리자 설정의 접힌 상세 영역에는 ‘실접속 / 자동접속 / 화면 합계’를 남겨 원인을 확인할 수 있게 한다. 일반 채팅·주문 행의 외형과 내부 분류는 분리한다. 실행 종료 후에는 자동 접속을 공개 숫자에서 제외하고 자동 메시지는 일반 회원 목록·새 실시간 이벤트에서 숨긴다. 관리자 주문 목록은 별도 삭제 전까지 정상 저장 상태로 남는다.


2. 실제 조사로 확인한 현재 상태

조사 기준은 2026-11-13 15:21 KST 무렵 DB와 원격 main 4f6a048이다. 이후 다른 개발과 자동 실행으로 달라질 수 있어 구현 시작 전에 다시 조회한다.

• 조사 시 자동 채팅 16행·닉네임 8개가 customer_id=4569에 연결돼 있었다. 브라우니 2행을 포함해 모두 avatar_url=autotest 표식이 있었다.

조사 보고서는 기존 ‘자동테스트_1단계_조사결과.txt’를 근거로 보존한다. 위 사항을 새로 수정했다고 보고하지 않는다.


3. 접근 방식 비교와 선택

A. 닉네임마다 실제 회원을 생성
장점: 서로 다른 회원의 로그인과 회원별 데이터 분리를 직접 검증할 수 있다.
단점: 회원·인증·연결 이력이 늘어나며 현재 1개 회원 구조 변경이 크다.
결정: 이번 기본 방식에서 제외. 서로 다른 카카오 회원 로그인 검증은 이 설계의 자동 회원 1개로 통과 판정을 내리지 않는다.

B. 모든 이용자를 실제 브라우저로 실행
장점: 화면과 영상까지 각 이용자별로 실행한다.
단점: 브라우저 실행 장치의 CPU·메모리·네트워크를 많이 쓰고 장시간 유지 비용이 커진다.
결정: 핵심 화면 검증용 소수 세션에만 사용한다.

C. 회원 1개 + 서버 접속 세션 + 소수 브라우저
장점: 기존 회원 재사용, 접속별 기록 분리, 장시간 유지, 낮은 실행 장치 부담, 실제 화면 확인을 함께 달성한다.
한계: API 접속은 동영상 디코딩·자동재생·기기별 UI를 검증하지 못한다. 실제 브라우저가 이 부분을 보완한다.
결정: 사용자가 마지막에 동의한 방향을 채택한다. 아래 숫자·스케줄·예산의 세부 기본값은 설계자가 정한 값이며 서버 측정 후 조정할 수 있다.


4. 전체 구성

관리자 기존 자동 실행 설정
  → 실행 범위와 독립 스위치를 DB에 저장
  → 서버 스케줄러가 실행할 작업을 원자적으로 확보
  → 독립 세션 A/B/C가 고객용 접속·채팅·장바구니·주문 API 호출
  → 기존 서비스의 공통 검증·저장 로직
  → 실제 DB 기록 및 기존 실시간 전파
  → 일반 회원 화면과 관리자 화면에서 확인

Gemini가 필요한 작업만
  → 공통 호출 관리자에서 프로젝트·모델·기능별 예산 사전 예약
  → 실제 모델 요청
  → 서버가 결과 검증
  → 허용된 채팅 전송

모든 작업은 run_id, actor_id, session_id, action_id로 연결한다. 별도 숫자 증가 API, 별도 가짜 주문 성공 API, 일반 고객 경로와 무관한 데이터 직접 삽입기는 만들지 않는다. 초기 자료 준비·마이그레이션과 런타임 고객 행위 실행은 구분한다.


5. 회원·닉네임·세션·인증 설계

5.1 회원 1개를 공유하되 닉네임은 세션마다 보관
• customer_id=4569는 자동 실행의 공통 소유 회원이다.
• actor는 가상 인물이다. 닉네임·말투·이모티콘 성향·행동 유형을 가진다.
• session은 그 인물의 독립 접속이다. 별도 UUID와 visitor_key, 장바구니 키를 가진다.
• 자동 실행 때 customers.youtube_nickname을 계속 덮어쓰지 않는다. 인증된 자동 세션 요청에만 서버가 actor의 닉네임을 주입한다. 일반 고객은 기존 회원 닉네임 규칙을 그대로 쓴다.
• 닉네임을 바꾸어도 actor_id/session_id/joined_at/leave_at은 유지한다. 이전 주문·채팅의 nickname_snapshot은 수정하지 않는다.
• 새 인물 입장은 새 세션을 만든다. 닉네임 변경은 입장으로 처리하지 않는다.
• 동일 campaign 전체에서 이미 사용한 닉네임과 변경 전 별칭을 원래 actor에 귀속시킨다. 퇴장·OFF/ON·run 변경 이후에도 다른 actor가 재사용하지 못한다. 실제 회원 닉네임과 충돌하는 후보도 재선정한다. NFC·공백·영문 대소문자 정규화 키를 UNIQUE(campaign_id, normalized_nickname)로 보호한다. 닉네임만으로 주문 삭제·권한 판단을 하지 않는다.
• 질문 후 미제출 주문이 있으면 닉네임 변경은 완료/취소 이후로 미룬다. 주문 인물은 해당 campaign의 주문 묶음이 끝날 때까지 표시 닉네임을 고정한다. 별도의 닉네임 변경 검증은 미제출 주문이 없는 비주문 인물로 수행한다.
• 원형 프로필은 표시 닉네임의 첫 grapheme을 사용한다. 브라우니→브, Jenny→J. 닉네임 변경 시 화면도 갱신한다.

5.2 인증과 데이터 접근
• 관리자 인증으로 실행을 생성한다. worker는 서버 전용 실행 권한으로 활성 run에 속한 제한된 세션만 생성할 수 있다.
• 브라우저 확인용 세션은 관리자 승인된 1회성 교환 코드로 발급하며, 짧은 수명·HttpOnly·Secure 쿠키로 해당 격리 브라우저에만 저장한다. 코드 재사용·만료·다른 run 사용을 거부한다.
• 서버 actor는 서명된 단기 토큰을 사용한다. run/session/expiry/권한 범위를 검증하며 서버 전용 비밀은 공개 응답이나 로그에 노출하지 않는다.
• 요청 본문의 kakao_id, is_test_order, session_id만 믿고 자동 계정 권한을 부여하지 않는다. 검증된 세션에서 customer·actor·내부 플래그를 확정한다. 예약된 자동 회원 ID로 일반 API를 호출했는데 유효한 자동 세션 인증이 없으면 거부한다. 일반 고객이 플래그를 보내 재고·결제 검증을 우회할 수 없어야 한다.
• 주문 조회·장바구니·채팅 개인 기록은 자동 세션에서 session_id로 추가 제한한다. 공유 customer_id 때문에 A가 B의 장바구니나 주문서를 조회·변경하면 안 된다.
• 계정 전체 속도 제한과 별도로 자동 세션 제한을 둔다. 계정 1개라는 이유로 모든 인물의 채팅이 하나의 간격 제한에 묶이거나 무제한으로 풀리지 않게 한다.
• 같은 브라우저의 고객 localStorage를 임시 교체하는 기존 ScreenTestHost 방식은 중단하고 격리된 브라우저 context로 교체한다.

5.3 데이터 구조
구현 명칭은 다음을 기준으로 하되 기존 동등 구조가 있으면 재사용한다.

automation_campaigns
  id, broadcast_id UNIQUE, status, config_revision, cancellation_epoch,
  last_submitted_at, next_order_at, scheduler_job_id.
  같은 사이트 방송의 반복 run·manual run이 공유하는 잠금과 주문 일정의 기준이다.
  동시에 활성인 반복 run은 campaign당 하나이며, 수동 run은 하나만 허용한다.

actor_nickname_aliases
  campaign_id, actor_id, normalized_nickname, display_snapshot,
  UNIQUE(campaign_id, normalized_nickname). 삭제/재사용으로 주문 상한을 우회하지 않는다.

automation_runs
  id, campaign_id, broadcast_id, customer_id, status, started_at, ends_at(nullable),
  orders_enabled, chat_enabled, viewers_enabled, presentation_mode,
  mode(repeat/manual), max_active, next_join_at, config_revision, stop_reason.
  주문 간격·취소 epoch·공유 scheduler는 campaign 값을 읽고 run마다 따로 초기화하지 않는다.
  status: prepared / running / draining / stopped / failed.
  presentation_mode: normal_live_check. 활성 run에서 공개 합산·일반 외형을 허용한다.
  ends_at은 선택 종료 시각이며 기본 NULL이다. NULL을 무조건 만료로 해석하지 않는다.
  campaign_id는 같은 방송에서 OFF/ON을 반복해도 유지하는 검증 묶음이다. 다른 방송은 새 campaign으로 분리한다.

automation_actors
  id, campaign_id, customer_id, nickname, style_seed, style_profile, behavior_kind,
  order_target_count, created_at, nickname_revision. 회원 테이블이 아닌 실행용 인물 기록이다.
  order_target_count는 주문 인물 1~3, 비주문 인물 0. 성공 수는 campaign/actor의 유일한 주문서 연결로 판정한다.
  같은 방송 내 새 run/새 session에서도 actor·닉네임·목표·말투는 유지한다. 삭제된 주문도 최소 tombstone으로 누적 수에 포함해 주문 상한을 재생성으로 우회하지 않는다.

automation_sessions
  id, run_id, actor_id, visitor_key UNIQUE, cart_session_key UNIQUE,
  driver(server/browser), watch_state, joined_at, leave_at, last_ack_at,
  auth_expires_at, stopped_at, revision.
  watch_state: scheduled / joined / watching / left / expired.
  시청 참여와 인증 수명을 구분한다. 시청자 OFF여도 이미 예약된 주문을 처리할 identity는 남길 수 있다.

automation_actions
  id, run_id, actor_id, session_id, kind, sequence, due_at, status,
  claim_owner, claim_until, fencing_version, attempts, result_ref,
  product_snapshot, source_message_id, order_idempotency_key.
  UNIQUE(run_id, session_id, kind, sequence). 답변은 source_message_id당 최대 한 번 처리한다.
  status: pending / claimed / succeeded / skipped / failed / uncertain / cancelled.

automation_links
  기존 주문·채팅·presence와 run/actor/session을 잇는 연결.
  신규 데이터는 대상 테이블의 nullable FK 칸 또는 동등한 연결 테이블로 저장한다.
  예: run_id, actor_id, session_id, order_group_id, chat_message_id, provenance.
  원래 주문 customer_id=NULL이던 과거 기록은 근거가 충분한 경우에만 보완한다.

ai_quota_policy / ai_usage_attempts / ai_usage_buckets
  검증된 모델·프로젝트 한도, 호출별 예약·결과, 잠금 대상 일일 집계.
  자동 기능과 관리자 AI 비서 사용량을 분리해 기록하면서 모델·프로젝트 총량을 함께 검사한다. 150회 고정 차단을 적용하지 않는다.

노출 스키마의 새 테이블에는 RLS를 적용한다. 관리·예산 테이블은 anon/authenticated 직접 접근과 Realtime 공개를 허용하지 않는다. 서비스 권한의 함수는 실행 권한을 명시적으로 제한한다. due/status, active run, session ID, idempotency key에 필요한 인덱스를 두며 전체 주문·채팅 테이블을 매 tick 전수 조회하지 않는다.


6. 접속 등록·유지·퇴장과 시청자 집계

6.1 같은 접속 처리 경로
• 브라우저는 기존 PresenceHeartbeat를 사용하되 인증된 자동 context에서는 viewers_enabled와 session 종료에 따른 중지 제어를 연결한다. 시청자 OFF/전체 OFF 종료 통지 또는 첫 SESSION_ENDED 응답을 받으면 heartbeat·재시도·자동 상태조회 타이머를 해제한다. 새 run/session 권한 발급 전까지 visibilitychange·online·재연결로 되살리지 않는다. viewers OFF인 주문 전용 자동 context는 처음부터 presence를 전송하지 않는다.
• 일반 관찰자 브라우저는 실제 이용 접속이므로 계속 열린 경우 기존 heartbeat를 유지하고 기준 인원에 포함한다. ‘OFF 뒤 자동 heartbeat 0회’는 자동 context만의 조건이며 일반 관찰자 트래픽을 중지시키거나 숨기지 않는다.
• 서버 actor는 자신의 인증과 visitor_key로 같은 /api/presence 경로를 호출한다. 서버가 존재한다고 가정해 presence 값을 직접 새로고침하지 않는다.
• 인증·정규화 후 기존 writePresence와 동일한 검증·저장 경로를 사용한다. 방송 ID와 시청 경로도 검증한다.
• 실제 API 성공 응답이 있어야 last_ack_at을 갱신한다. 실패한 요청을 성공 처리하거나 미래 시각을 기록하지 않는다.
• 브라우저 driver의 세션을 서버가 대신 heartbeat 하지 않는다. 브라우저를 닫았는데 서버가 계속 살려 두는 유령 접속을 방지한다.

6.2 집계 규칙
• 기본 인원 단위는 기존과 같은 독립 visitor_key다. 서로 다른 실제 사람 수로 재해석하지 않는다.
• 같은 context의 새로고침·중복 탭은 기존 visitor_key 정책을 유지한다. 별도 context/기기는 별도 접속으로 센다.
• 같은 session에서 browser와 server driver가 동시에 활동하지 못한다. 소유권 전환 시 revision을 바꿔 이전 driver의 쓰기를 거부한다.
• 유효 접속: last_seen_at이 서버 현재 시각 기준 최근 75초 이내이고, 명시적으로 종료되지 않았으며, 자동 세션이면 run과 leave_at도 유효해야 한다.
• 눈 숫자: 현재 대상 방송의 시청 경로에 있는 유효 접속 수.
• 사이트 숫자: 관리자 경로를 제외한 사이트 전체 유효 접속 수.
• 현재 방송의 공개 합산: 유효한 실접속 + 해당 방송의 공개 실행에 속한 유효 자동접속. 다른 방송의 자동접속은 합산하지 않는다.
• 별도의 가상 배열 길이, 저장된 주문 닉네임 개수, 채팅 수를 더하지 않는다.
• 합계는 집계 시 파생한다. ‘이전 값+1’ 누적 카운터로 인원을 유지하지 않는다.

6.3 갱신과 허용 지연
• heartbeat 기본 30초. 서버 시각을 사용한다.
• 정상 퇴장: leave API로 ended_at 기록, 집계 캐시 무효화 후 화면 반영.
• 강제 종료/네트워크 끊김: 마지막 heartbeat+75초에 만료.
• 기존 집계 캐시 8초와 화면 갱신 주기 최대 10초를 감안해 정상 입퇴장 화면 반영 목표는 20초 이내, 신호 끊김은 95초 이내로 잡는다. 이는 합격 기준이며 무조건 보장되는 수치라고 표시하지 않는다.
• 실시간 이벤트가 유실되면 기존 폴링으로 복구한다. 오래된 응답에는 sequence/revision을 비교해 최신 숫자를 덮어쓰지 못하게 한다.
• join·leave의 중복 요청, 지연 도착 heartbeat, 만료 토큰은 인원을 되살리지 않는다. 새 입장은 새 session으로 처리한다.

6.4 체류시간
5·10·30·60·120분 중 하나를 동일 확률로 선택한다. 기존 ±20% 변동을 제거한다. joined_at에 선택 시간을 더해 leave_at을 저장하며 닉네임 변경으로 수정하지 않는다.

초기 자동접속 상한은 5개, 설정 가능한 1차 상한은 10개로 둔다. 입장 간격은 30~90초 범위에서 서버가 선정한다. watch 상태에 들어간 세션에만 눈 숫자를 반영하며 상품 목록·주문 화면으로 이동하면 사이트 숫자에는 남고 눈 숫자에서는 해당 화면 정책대로 빠진다.

실행 전체 길이를 2시간으로 강제하지 않는다. 기본은 관리자가 켜둔 기능만 반복하고 OFF 또는 사이트 방송 종료 때 멈춘다. 5~120분은 각 인물의 체류시간이며 전체 실행시간이 아니다. 선택적으로 종료 시각을 정한 경우에만 그 시각 내 체류 가능한 후보를 고르고, 5분 미만이면 새 입장을 중지한다. 관리자 중단·방송 종료·부하 보호는 예정 체류보다 우선한다.

한 인물의 체류가 끝나면 다른 인물이 들어올 수 있으나 활성 접속 상한을 지킨다. 같은 방송의 OFF/ON은 새 회원·새 AI 예산·새 주문 목표를 만들지 않는다. 사이트 주문 본격 시작 여부를 AI나 첫 주문 1건으로 추정해 자동 전환하지 않는다. 운영자가 기존 스위치를 모두 끄는 것이 반복 운영의 종료 조작이다. 다른 방송까지 자동으로 켜지지 않는다.


6.5 실제 화면에서 관찰할 예시
관찰용 일반 브라우저 1개가 방송 화면을 계속 보고 있다는 기준이다. 주문용 브라우저 등 다른 접속이 있으면 그 수를 기준 인원에 추가한다.
  시작                     눈 1
  A 입장                   눈 2
  B 입장                   눈 3
  C 입장                   눈 4
  A 퇴장                   눈 3
  D 입장                   눈 4
  B와 C 퇴장               눈 2
  D 퇴장                   눈 1
각 변화는 실제 접속 요청과 집계 결과로 검증하며 위 숫자를 화면에 강제로 주입하지 않는다. A가 방송 화면에서 상품 목록으로 이동하면 눈 숫자는 줄고 사이트 숫자는 유지되는 경우도 별도로 확인한다.


7. 브라우저를 많이 열지 않는 서버 실행 방식

7.1 초기 구성
• 서버 actor 최대 5개: 장시간 접속·입퇴장·대부분의 주문·채팅 요청 실행.
• 실제 브라우저: 기본 2개 context. 하나는 일반 회원 화면 관찰·실제 재생, 하나는 사이트 화면을 통한 상품 선택·주문서 제출 검증. 두 context는 저장소를 공유하지 않는다.
• 실제 브라우저도 사이트에 접속하면 실제 집계 대상이다. 검증자가 보고 있다는 이유로 숫자에서 몰래 제외하지 않고 기준 인원에 포함한다.
• 브라우저 최대 3개 context로 모바일·PC 교차 검증을 추가할 수 있다. API actor와 브라우저 driver를 합친 자동 세션 수는 run.max_active를 넘기지 않는다.
• 관찰자 기기의 메모리 사용량과 서버·DB 부하는 따로 측정한다.

7.2 예약 실행과 OFF 시 호출 중지
확인된 pg_cron 1.6.4의 30초 예약과 Supabase pg_net을 사용하는 안을 채택한다. pg_net은 미설치이므로 구현 전에 확장 지원·권한·잔여 한도를 확인한다. 새 유료 서비스·상시 브라우저 서버는 만들지 않는다.

ON 저장 RPC는 관리자 권한과 config_revision을 확인하고 한 트랜잭션에서 기능 설정·run·고유한 scheduler job의 활성 상태를 함께 바꾼다. 방송/campaign 잠금으로 여러 관리자가 동시에 눌러도 job 하나만 존재하게 한다. cron 내부 DB 호출은 현재 실행할 due 작업이 있을 때만 Vault의 서버 자격으로 HTTP를 보낸다. heartbeat/입퇴장과 AI/주문 작업은 분리해 AI 응답 대기가 접속 갱신을 막지 않는다. 장시간 함수·무한 루프·분 단위 sleep은 사용하지 않는다.

모든 기능 OFF를 저장하는 같은 DB 트랜잭션에서 신규 claim 차단, 자동 presence 종료, 미실행 action 취소, 자동 장바구니 해제, 공개 채팅 노출 종료와 cron job 비활성화를 확정한다. 외부에 이미 전달된 요청은 revision/fencing 검사로 늦은 쓰기를 차단한다. 정리용 마지막 응답·이미 전송된 요청이 끝나는 데 필요한 사용량은 남지만, 이후 반복 tick/HTTP/AI는 없어야 한다. 일부 기능만 OFF이면 남은 기능에 필요한 job만 유지한다. cron 관리 권한은 서버 전용 RPC로 제한하고 클라이언트 SQL 실행은 허용하지 않는다.

기존 vercel.json의 /api/cron/auto-test-order 매분 예약은 새 실행기 전환 배포에서 제거한다. OFF 상태를 확인하려고 매분 깨우는 watchdog으로 남기지 않는다. Bankda·주문 읽기·장바구니 정리·방송 지표 등 다른 서비스의 예약은 유지한다. 예전 배포와 새 배포가 겹쳐도 기존 자동 실행 엔드포인트는 실행 소유권을 검사해 행위를 만들지 못하게 한다. 실제 운영 프로젝트의 예약 목록에서도 제거됐는지 확인한다.

전체 OFF 상태에서는 자동 설정 전용 30초 폴링도 중지한다. 최초 화면 진입·탭 복귀·직접 조작 때 한 번 최신 상태를 읽는다. 다른 관리자 조작 통지는 이미 있는 관리자 공유 구독이 있다면 재사용하며 OFF 확인만을 위한 새 상시 연결은 만들지 않는다. ON 상태의 상태 조회도 보이는 탭에서만 하고, 조회 GET 자체가 작업을 실행하지 않도록 한다.

ON/RPC 원자성 실패는 전체 rollback해 켜짐으로 표시하지 않는다. 서비스 재시작은 DB의 enabled와 활성 job을 복구 기준으로 삼고 임의로 OFF를 ON으로 바꾸지 않는다. DB 복구·배포 점검 때 scheduler 불일치를 확인하며, 수동 ON 재요청은 기존 job을 중복 생성하지 않는 복구 경로다. 전달 지연·예약 장애 때 실패를 숨기거나 화면 숫자를 가산하지 않는다. pg_net/30초 전달을 사용할 수 없다면 이 실행안의 지속 동작은 미검증으로 두며 기능이 구현됐다고 보고하지 않는다.

자원 중지의 범위: 전체 OFF 안정 상태에서는 이 자동 기능의 정기 Vercel 호출·heartbeat·채팅·주문·Gemini 요청 0회가 목표다. 기존 사이트 접속, 다른 업무 cron, DB 기본 서비스, 사용자 직접 클릭까지 사용량 0이 되는 것은 아니다. Vercel 공식 문서상 cron도 함수를 호출하므로 함수 사용량에 포함되고, 실패 응답이나 즉시 return도 호출 자체를 없애지는 못한다.

7.3 작업 중복과 재시작
• DB에서 FOR UPDATE SKIP LOCKED 또는 동등한 원자적 claim을 사용한다. 짧은 lease와 증가하는 fencing_version을 발급한다.
• 외부 HTTP/Gemini 대기 동안 DB 트랜잭션을 열어 두지 않는다.
• 작업 실행 직전 run 상태·스위치·revision·lease를 다시 확인한다.
• worker가 종료되면 lease 만료 후 다른 worker가 작업을 회수한다. 주문 재전송은 같은 idempotency key를 쓴다.
• 서버 재시작 시 마지막 신호가 아직 75초 유효기간 안이면 같은 session으로 이어갈 수 있다. 이미 75초를 넘겨 만료된 session은 다시 살리지 않는다. actor의 원래 leave_at이 남아 있으면 새 session/visitor_key를 만들고 reconnect_of로 연결한다. 새 session의 leave_at은 원래 시각을 그대로 상속하며 체류시간을 새로 뽑거나 늘리지 않는다. 이전 session은 ended 상태로 고정하고 동시 유효 접속은 하나만 허용한다. 끊긴 시간은 소급 채우지 않으며 연속 체류 검증은 실패로 남긴다. 기존 주문·채팅 action은 원래 identity에 남겨 중복 실행하지 않는다.
• 브라우저 종료 시 server driver는 계속 동작하지만 browser driver는 만료된다.
• 질문 뒤 대기·입장·퇴장·답변 예정은 due_at으로 저장한다. 타이머 메모리만으로 관리하지 않는다.

7.4 부담 예상과 제한
30초 heartbeat인 서버 세션 5개는 heartbeat만 분당 약 10회, 시간당 600회다. 스케줄러 HTTP 요청이 30초마다 1회이면 시간당 약 120회가 추가된다. 즉 2시간 기준 이 두 항목은 약 1,440회다. 세션 5개를 24시간 고정 유지하면 heartbeat만 14,400회가 되므로 ‘가벼우니 무제한 무료’라고 설명하지 않는다.

여기에 브라우저 폴링·페이지 요청·채팅·주문·DB 조회·실시간 전파가 추가된다. 이 계산은 청구액이나 처리 가능 인원의 보장이 아니다. 브라우저는 기본 2개 context, 자동 주문은 같은 방송 campaign 전체에서 5~10분당 1건, AI 생성 동시성은 프로젝트 전체 1개를 초기값으로 잡는다.

기준 측정 10분 후 1→3→5세션으로 올린다. 아래는 초기 정지 기준이다.
• 새 내부 5xx 3회 연속: 신규 자동 행위 정지, 상태 확인.
• p95 응답 지연이 기준의 2배를 넘고 절대 2초 초과 상태가 2분 지속: 신규 입장·주문 중지.
• heartbeat 2회 연속 실패: 해당 세션 단절로 기록하며 정상 인원처럼 유지하지 않음.
• 인프라 사용량 한도 접근: 신규 작업을 중단하고 활성 세션 종료 처리만 수행.
대규모 동시 주문 부하 검증은 이 5세션 실사용 확인과 별개 단계다. 소규모 결과로 방송 중 수백 명의 처리 능력을 보장하지 않는다.


8. 상품·장바구니·주문 설계

8.1 주문 기본 규칙
• 주문 실행 간격은 같은 방송 campaign 전체의 실제 자동 제출 시각 기준 5~10분 랜덤이다. 인물별로 각각 5~10분 주문을 만들어 총량을 늘리지 않는다. 정상 dispatch에 30초 여유를 두어 다음 제출 예정은 직전 제출 후 300~570초 범위에서 선택한다. 질문 준비는 해당 예정 시각보다 약 90~120초 앞서 시작한다. 질문 뒤 대기시간을 5~10분 간격에 추가해 제출 간격이 6~12분으로 늘어나는 구조를 만들지 않는다. 실제 질문 게시 후 다음 제출까지 30초를 확보할 수 없으면 그 차례는 질문 없이 주문한다. 600초를 넘긴 지연은 기준 미달로 기록한다.
• 주문하는 닉네임 하나가 제출할 서로 다른 주문서는 1~3건이다. 별도 order_group_id 1개를 주문서 1건으로 센다. 주문 안 상품행 3개·수량 3개·같은 요청 재전송은 주문서 3건이 아니다.
• 인물 생성 때 목표를 1/2/3건 중 정하고 동일 방송 내 OFF/ON·새로고침·재연결로 다시 뽑지 않는다. actor당 미제출 주문은 하나만 예약하며 목표를 채운 닉네임은 더 주문하지 않는다. nickname 변경으로 상한을 피하지 못하게 actor/campaign 기준으로 집계한다.
• 시청만 하는 인물은 0건으로 두고, 주문 인물은 남은 체류와 전체 슬롯 안에서 목표 달성이 가능한 경우에 배치한다. 3건 목표는 원칙적으로 30분 이상 체류와 최소 3개의 예약 가능 슬롯이 있을 때만 선정한다. 슬롯이 부족하면 신규 주문 인물 배치를 미루거나 더 작은 목표를 먼저 정한다. 정한 목표는 도중 OFF·품절·장애 때문에 미달할 수 있으며 억지로 제출하거나 체류를 연장하지 않는다. 상품이 판매 가능한 정상 조건에서는 1~3건 완료를 검증한다.
• 주문서에는 현재 방송의 판매 가능한 실제 상품을 담는다. 초기 기본은 상품 1종이며 필요하면 실제 장바구니 허용 범위에서 추가한다. ‘1~3종’이라는 별도 요구로 해석하지 않는다. 각 상품 수량은 1~3개를 초기값으로 하되 실제 재고·구매 제한을 따른다. 옵션은 등록된 값만 선택한다.
• 기존의 ‘11월 6일 이후 주문 이력 있는 상품’ 같은 날짜 고정 필터는 제거하고 현재 방송 상품 기준으로 바꾼다. 명시적인 판매 제한은 유지한다.
• 카드/무통장 선택은 실제 주문 화면 조건을 따른다. 최소 결제액 등 조건상 불가능한 수단을 강제로 선택하지 않는다.
• 금액·배송비·옵션·수량 검증은 기존 고객 주문과 동일한 함수/RPC를 사용한다.
• 장바구니 예약은 실제 경로를 호출하지만 자동 세션 예약은 실제 고객의 가용 재고를 점유하지 않는 별도 검증 예약으로 저장한다. 실재고 조회·옵션 품절 검증은 수행한다.
• 주문서 데이터는 실제 orders 및 관리자 목록에 저장한다. 서버가 인증된 세션을 확인하고 내부 제외 플래그를 강제한다.

8.2 질문과 주문 연결
1. 현재 방송·송출 상태와 실제 ‘지금 보는 상품’ 카드의 revision을 읽는다.
2. 상품 ID, 세부상품 ID/명, 옵션 ID, 당시 이름·가격·카드 revision을 snapshot으로 저장한다.
3. 충분한 체류시간이 남은 actor/session을 선택한다. 재생 중인 라이브이고 카드가 있을 때만 상품 질문 생성 예산을 요청한다.
4. 생성 결과의 product_id가 snapshot과 다르면 폐기한다. 전송 직전 카드가 바뀌었다면 질문을 보내지 않으며 이미 소비한 AI 횟수는 되돌리지 않는다.
5. 8.1에서 정한 제출 예정 P를 유일한 주문 due_at으로 유지한다. 질문 준비는 P보다 90~120초 전에 시작하고, 질문 게시 예정은 P보다 30~90초 이른 시각에서 무작위 선택한다. 실제 게시 허용 창은 P-90초~P-30초다. 너무 이르면 대기하고 늦었으면 그 차례의 질문은 생략한다. DB created_at을 asked_at으로 저장하고 P-asked_at 30~90초를 검사한다. 질문 저장 후 P를 다시 덮어쓰지 않는다. 주문은 P부터 최대 30초 dispatch 여유 안에 실행하여 실제 질문 저장부터 주문 저장까지 30~120초를 목표로 한다. 전송/DB 지연 때문에 목표를 넘기면 통과로 보고하지 않는다. 질문 게시가 이미 늦어 실제 주문까지 30초를 확보할 수 없으면 해당 질문 연결 주문을 취소하고 다른 상품으로 대체하지 않는다.
6. 주문 차례에는 저장한 질문 상품을 반드시 포함한다. 같은 actor·동일 nickname_snapshot을 유지하고, 이 주문서가 해당 닉네임의 1~3건 중 몇 번째인지 연결한다.
7. 카드가 바뀌어도 질문했던 상품이 판매 가능하면 그대로 주문한다. 삭제·판매중지·품절이면 제출 전 조회에서 즉시 취소하고 주문서 제출 API를 호출하지 않는다. 주문 행·실패 주문서·주문 완료 채팅도 만들지 않는다. 다른 상품을 대체하지 않고 예약만 해제한다. 내부 action에는 건너뜀 사유만 보관할 수 있으나 고객 화면이나 새 로그 화면에 노출하지 않는다.
8. 옵션·수량·가격은 제출 직전에 다시 검증한다. 사용자 질문과 다른 옵션을 임의로 꾸며 넣지 않는다.
9. 장바구니 → 제출 직전 판매/옵션/수량 재조회 → 주문서 제출 → 저장 확인을 같은 session과 idempotency key로 실행한다. 사전 조회 이후 품절되는 경쟁 상황은 주문 저장 트랜잭션의 동일 검증에서 차단해 주문 행이 남지 않게 한다. 사전에 이미 품절임을 알면서 검증 실패를 얻으려고 제출하는 방식은 금지한다.
10. 저장된 주문의 상품 ID·옵션·수량·닉네임·세션을 계획과 비교한 후에만 주문 관련 채팅을 보낸다.

질문 전송 실패 시 ‘질문 후 주문’으로 기록하지 않는다. 스케줄러가 늦어 질문 후 120초를 이미 넘긴 미제출 작업은 취소하며 시간 조건 미달로 남긴다. DB 작업 중복 때문에 억지로 맞춘 시각을 기록하지 않는다.

8.3 AI 중단과 스위치 변경
• AI 한도 부족: 질문 생성 없이 일반 주문 실행.
• 채팅 OFF: 미전송 질문·인사·답변을 취소. 이미 질문한 주문은 저장된 상품과 인물로 이어가되 이후 채팅은 보내지 않음.
• 주문 OFF: 신규·미제출 예약 주문 취소. 이미 제출된 주문은 유지.
• 접속 OFF: 공개 집계용 시청 참여를 종료. 주문·채팅이 ON이면 별도 활동 identity로 계속 실행하되 시청자로 재등록하지 않음.

8.4 금전·재고·알림 보호
내부 자동 플래그는 주문 저장 트랜잭션에서 확정한다. 생성 이후 비동기로 붙이는 방식은 사용하지 않는다. 상품/주소/금액 검증은 동일하게 실행하지만 부수 효과만 내부 context로 차단한다.
차단 대상: PG 승인·결제 링크 실발송, 실제 입금 데이터 연결, Bankda 매칭, 재고 증감·예약 점유, 매출·정산·부가세 집계, 포인트 지급/차감, 배송·송장·피킹, 쿠폰/선물/첫주문 혜택, 문자·알림톡·유튜브 외부 발송.

카드 선택은 주문서 제출과 결제 대기 화면까지만 확인한다. 무통장도 실제 입금확인으로 변경하지 않는다. 기존 자동 주문에 대한 수동 입금확인 예외는 실거래 연결을 허용하지 않도록 제거하거나 내부 상태 검증으로 분리한다. 실제 결제 완료가 없는 이번 실행에서는 ‘결제 완료’ 채팅을 보내지 않는다.

같은 요청이 timeout 난 뒤 재전송돼도 주문서 하나만 저장되도록 주문 제출 경계에 idempotency를 둔다. 응답 유실은 같은 키로 저장 상태를 조회해 해결하며 새 주문번호로 재시도하지 않는다. 서버가 결과를 확정하지 못하면 uncertain으로 두고 자동 재주문을 멈춘다.

8.5 개별·일괄 영구 삭제
기존 삭제 기능을 유지한다. 서버는 대상 주문서 전체가 내부 자동 데이터인지 다시 검사하고 일반 주문이 한 행이라도 섞였으면 해당 주문서를 삭제하지 않는다. 대상 ID 목록은 관리자 권한·현재 조회 범위와 함께 확인한다.
삭제 중 대상 주문 재시도·새 채팅이 생성되지 않도록 관련 action을 취소한다. 주문과 안전하게 연결된 메시지·장바구니 예약을 정리한다. 닉네임 문자열만으로 채팅을 삭제하지 않는다. 원래 고객 메시지·기존 회원·실입금 기록은 삭제 대상이 아니다. 주문 삭제 후에도 중복 제출 방지용 최소 tombstone은 개인정보 없이 보존한다.


9. 채팅과 실제 시청자 응답

9.1 기본 행동 배분
초기 행동 비율은 시청만 40%, 인사·일반 대화 20%, 질문 후 주문 30%, 질문 없이 주문 10%로 제안한다. 상품 질문을 올리는 인물은 모두 실제 주문 슬롯과 연결한다. 주문 OFF·목표 소진·체류 부족·슬롯 부족이면 상품 질문을 생성/게시하지 않는다. 채팅만 ON이면 인사·일반 대화·허용된 직접 답변은 가능하지만 주문 약속을 만드는 상품 질문은 하지 않는다. 비율은 행동 성향이며 주문 전체 5~10분 간격을 넘겨 별도 주문을 생성하지 않는다. AI 예산이 없으면 상품 질문을 생략하고 주문 여부는 기존 계획대로 결정한다.

말투는 actor에 저장하고 같은 방송의 OFF/ON·재연결 전후에도 유지한다. 일반 채팅은 actor당 최소 3분 간격, 한 세션에서 일반 인사 최대 2회로 시작한다. 인사·편의성 감상·이모티콘·닉네임은 서버 문장 목록과 랜덤 선택으로 처리한다. 동일 문장은 같은 run 최근 20개와 같은 actor 최근 5개에서 반복을 피한다. 이모티콘은 보통 0~1개다.

요청서의 사이트 이용 편의성 문장도 자동 문장 목록에 포함하되 영구 고객 후기·상품 리뷰·홍보 소재로 전환하지 않는다. 해당 run이 끝나면 다른 자동 채팅과 같은 노출 종료 규칙을 적용한다.

9.1.1 인물별 말투와 일관성
30·40·50대 × 남녀를 포함한 가상 설정을 골고루 준비한다. 나이·성별은 인물 구성의 배경일 뿐 ‘남자는 짧게, 여자는 애교’처럼 고정하지 않는다. 같은 나이·성별 안에서도 말투가 다른 인물을 만들고, 실제 고객 메시지로 고객의 나이·성별을 분류하지 않는다. 가상 나이·성별은 공개 프로필이나 채팅에서 굳이 말하지 않는다.

style_profile에 존댓말 정도, 문장 길이, 주로 쓰는 어미, 자주/드물게 쓰는 단어, 띄어쓰기 성향, 문장부호, 웃음 표현, 이모지 빈도, 질문 관심사, 반응 속도, 구매 맥락을 저장한다. 설정된 체형·사이즈나 선물 대상이 있으면 다음 질문에서도 모순되지 않게 하되 실사용 후기를 지어내지 않는다. 기본값은 서버의 여러 조합으로 선정하고 질문할 때마다 설정을 다시 생성하지 않는다.

말투 예시 — 아래는 허용된 상품 정보를 묻는 형식 예시이며 그대로 반복하는 고정 문장 목록이 아니다.
• 30대 남성 설정 / 간결하고 정중: ‘이거 세탁은 어떻게 하면 돼요?’
• 30대 여성 설정 / 담백하고 비교 중심: ‘두 색 중엔 어떤 게 더 밝아요?’
• 40대 남성 설정 / 차분한 완문: ‘선물하려고 보는데, 길이 한번 확인 부탁드려요.’
• 40대 여성 설정 / 짧고 친근: ‘옆모습도 좀 보여주세요~’
• 50대 남성 설정 / 부드럽고 짧음: ‘네 잘 보고 있어요.’
• 50대 여성 설정 / 정중하고 구체적: ‘소매 끝부분을 가까이 볼 수 있을까요?’
모든 문장은 실제 카드의 종류·색상·설명과 맞을 때만 사용한다. 같은 설정군에서도 차분함/활발함, 장문/단문을 교차 배정해 성별·연령별 상투어가 되지 않게 한다.

Gemini 한 요청에 상품 snapshot, 방송 상태/KST, 이 인물의 style_profile, 자기 최근 5개 발언, 해당 직접 대화 문맥, 전체 최근 20개 중복 회피 요약을 함께 전달한다. 질문/답변 생성과 맥락 판단은 한 번에 하고 별도 ‘말투 분석 AI’를 매번 호출하지 않는다. 다른 인물의 개인정보나 실제 고객 주문 내역은 보내지 않는다.

전송 전 서버가 반복·상품 불일치·없는 사실·시스템 용어를 검사한다. 전체 최근 20개에서 정규화 완전일치는 차단하고, 같은 상품/질문 intent의 유사 문장도 단어 3-gram Jaccard 0.8 이상이면 기본 차단한다(초기 조정값). 같은 인물의 반복 시작말·어미와 전체 인물의 ‘언니/ㅎㅎ/감사합니다’ 쏠림은 별도 분포로 점검한다. 짧은 문장은 완전일치/intent 기준을 사용한다. 걸린 문장은 추가 AI 호출로 무한 수정하지 않고 해당 발언을 생략하거나 같은 인물 스타일의 검증된 후보를 사용한다. 캐시 키에는 style_profile 버전과 인물별 최근 사용 이력을 반영한다.

인사·주문 제출 확인 등 서버 문장도 각 말투군별 충분한 후보를 갖추고, 실제 주문 저장 성공 때만 1회 보낸다. 모두가 주문 직후 같은 감사 인사를 보내거나 같은 이모지를 붙이지 않는다. 고의 오타·과도한 사투리·성별 고정관념으로 자연스러움을 흉내 내지 않는다. ‘AI라서/테스트 중/시스템 확인/API/한도 초과’ 같은 내부 상태를 공개 채팅으로 보내지 않는다.

품질 통과는 ‘어떤 사람도 AI임을 알아차릴 수 없다’는 보장이 아니다. 자동화 출처를 일반 문구로 노출하지 않고, 서로 다른 인물처럼 일관되게 자연스러운 한국어를 쓰는지가 검증 대상이다. 최소 12인물(6설정군 × 2스타일)의 질문·직접 답변·주문 후 발언 샘플을 오프라인에서 검토한다. 실제 방송에 샘플을 몰아서 게시하지 않는다. 사람이 발언만 읽었을 때 반복·설명체·상품 모순이 드러나면 수정하고, 일반 회원 화면의 글과 실제 actor 연결까지 확인한다.

9.2 상품 질문
카드·유효한 주문 예약 슬롯이 없거나 실제 라이브가 아니면 상품 AI 질문을 생성하지 않는다. 상품 종류는 기존 구조화 데이터가 우선이다. 여성 의류 질문은 실제 상품 분류가 의류인 경우만 허용한다. 마야는 성별·사이즈를 단정하지 않고 등록 정보에 따른다. 다이슨/가전과 불명확한 종류에는 키·몸무게·착용 사이즈 질문을 금지한다.

상품명이 임의로 의류처럼 보인다는 이유만으로 분류하지 않는다. 등록되지 않은 색상·옵션·가격을 단정하는 문장을 거부한다. Gemini의 구조화 결과는 question, intent, product_id, tone, emoji를 한 번에 받아 검증한다. 주문 후 문구는 생성하지 않고 서버가 실제 주문 상태로 고른다.

질문 재사용 캐시는 product ID + 세부상품 + catalog revision + question type + 방송 모드로 묶는다. 상품 변경 시 무효화한다. 캐시 문장은 전송 직전 현재 카드·정보를 다시 확인하며 같은 질문을 반복 게시하기 위한 용도로 사용하지 않는다.

9.3 실제 이용자의 직접 언급
• 인간 메시지의 reply_to 또는 정확한 닉네임 mention을 규칙으로 검사한다. 모호한 부분 문자열 일치는 제외한다.
• 자동 actor·봇·시스템 메시지에는 답하지 않는다. 자동 인물끼리 답변을 주고받아 호출량이 늘어나는 것을 막는다.
• 대상 actor가 활동 중이고 채팅 ON일 때만 응답 후보를 만든다. 숨김/삭제 메시지나 이미 답한 message_id는 제외한다.
• 가격 확정·재고 보장·배송일·환불·운영자 권한이 필요한 내용은 AI로 판단하지 않고 답변을 생략하거나 준비된 운영자 문의 안내 한 줄만 허용한다.
• 복잡한 직접 질문만 Gemini 한 번으로 의도·응답 가능 여부·답변을 함께 생성한다. 이해가 안 되거나 정보가 없으면 무응답.
• 문맥은 해당 직접 대화의 최근 제한된 메시지만 보낸다. 개인정보·주문 상세·전화번호를 보내지 않는다. 사용자 글과 상품 설명은 지시가 아닌 데이터로 전달한다.
• 답변 예정은 10~30초 후로 랜덤 설정하며 30초 dispatch 주기를 포함한 실제 전송 목표는 10~60초다. 스케줄러 지연은 기록하며 브라우저 타이머에 의존하지 않는다.
• 초기 제한: actor당 10분에 AI 응답 1회, 같은 인간과 같은 actor는 30분당 최대 2회, 인간 1명에 대한 전체 자동 응답은 10분당 2회. message_id 전체에서 하나의 답변만 선택한다.
• 여러 actor가 언급되면 명시적 답글 대상을 우선하고, 명확하지 않으면 답하지 않는다.
• 생성 결과 전송 전에 채팅 ON·원문 존재·중복·actor 상태를 재검증한다. 직접 답변에 주문 슬롯 없는 새로운 상품 질문을 덧붙이지 않는다.


10. 한국 시간과 방송 상태

시간 기준은 DB/서버 UTC instant다. 표시·인사·사이트 AI 일일 한도는 Asia/Seoul로 변환하고, Google RPD는 America/Los_Angeles로 계산한다. 클라이언트 시계를 스케줄 판정에 쓰지 않는다.

인사 범위는 05:00~10:59 아침, 11:00~16:59 낮, 17:00~20:59 저녁, 21:00~04:59 밤이다. 모든 글에 인사를 넣지 않는다. 모호하면 ‘안녕하세요’로 대체한다. 생성 직전과 전송 직전 각각 계산해 경계 시각을 건넌 문장도 검증한다. 부적절한 문장은 재생성 대신 준비된 문장으로 바꾼다.

방송 모드:
LIVE: 사이트 방송 활성 + 해당 영상의 신선한 실제 송출 증거. 상품 질문 가능.
PAUSED: 서버의 유효한 휴식 상태. 가벼운 인사·상품 구경, 질문 생성 중지.
REPLAY: 실제 송출 종료 확인 + 유효한 다시보기 서비스. 주문은 상품 판매 조건에 따라 가능.
ENDED: 사이트 종료 또는 다시보기 없음. 신규 상품 질문·시청 입장을 중지.
UNKNOWN: 송출 데이터 누락/오래됨/상충. 라이브로 추정하지 않으며 AI 상품 질문 중지.

기존 유튜브 상태 수집·캐시를 재사용한다. 단순 시청자 수 0은 종료 근거가 아니다. 오래된 숫자나 종료 버튼 미클릭만으로 라이브라고 보지 않는다. 매 actor마다 유튜브 API를 추가 호출하지 않는다. 유튜브 원본 시청자 수는 수정하지 않는다.

주문 완료 문구는 서버가 해당 세션의 주문 제출 성공을 확인한 경우만 전송한다. 질문 생성 당시 준비한 ‘주문했어요’를 시간만 지났다고 게시하지 않는다.


11. Gemini 중앙 제어와 무료 사용

11.1 확인값과 미확인값
원격 코드의 허용 모델은 gemini-3.5-flash-lite, gemini-3.1-flash-lite, gemini-3.8-flash다. DB에 첫 번째 모델 예약 기록이 있었다. 실제 런타임 모델은 성공 응답·설정·호출 기록으로 다시 확인한다.

사용자가 추가로 제공한 AI Studio 실측 결과:
• 무료 등급이며 결제 계정이 연결되지 않았음.
• 주 모델 3.5 Flash Lite: RPM 15, RPD 500. 최근 28일 중 일일 최대 사용 142회.
• 예비 모델 3.1 Flash Lite: RPD 500.
• 예비 모델 3.8 Flash: RPD 20.
이 내용은 사용자가 제공한 실측값이며 이번 설계 수정 중 AI Studio에 직접 접속해 재측정한 값은 아니다. 3.1/3.8의 RPM과 각 모델 TPM, 연결할 정확한 project/model ID는 실행 전 보완한다. 과거 최대 142회는 여유를 가늠하는 자료이지 앞으로의 사용량 상한이 아니다.

현재 관리자 N/150은 일부 경로를 특정 시점부터 센 사이트 카운터이며 Google 프로젝트 전체 사용량이나 실시간 잔여량과 동일하지 않다. 이를 500회 전체 예산 관리의 근거로 그대로 사용하지 않는다.

Google의 제한은 프로젝트 범위에서 모델별 적용 항목을 확인해야 하며 RPM·TPM·RPD를 각각 만족해야 한다. RPD 초기화는 태평양 시간 자정이다. 500+500+20을 확인 없이 공유 총량 1,020회로 취급하지 않는다. 검증된 정확한 model ID만 허용하고 latest 별칭은 사용하지 않는다.
근거: https://aistudio.google.com/docs/rate-limits

11.2 정책 저장
정책에는 verified_at, expires_at, project fingerprint, exact model ID, free tier 확인, billing 미연결 확인, RPM/RPD/TPM, 안전 여유, 외부 사용 기준값, 허용 기능을 저장한다. 비밀 API 키는 저장하지 않는다.
정책 유효기간 초기값은 확인 후 24시간, 운영 중 오류·등급 변경 징후가 있으면 즉시 무효화한다. 유효기간 만료·한도 불명·정책 읽기 실패 시 AI만 중단한다. 재검증 전 새로운 모델을 자동으로 추가하지 않는다.

주 모델의 설계상 기본 운영 상한은 전체 기능 합계 RPD 450, 최근 60초 RPM 13으로 높인다. 제공자 한도 500/15와 구별되는 10% 안팎의 안전 여유이며 고정된 Google 규정이 아니다. 자동 질문만 450회가 아니라 같은 모델을 쓰는 질문·답변·AI 비서·재시도·기타 기능의 합계다. 실제 TPM과 별도 프로젝트 제한이 더 낮으면 그 조건이 먼저 적용된다.

남은 예산 = 운영 상한 - 해당 Google 집계일의 모든 소비 예약 - 중앙 도입 전/외부 사용량의 보수적 offset.
‘소비 예약’에는 진행 중·성공·실패·전송 불명 시도가 이미 포함되므로 같은 요청을 이중 차감하지 않는다. offset도 중앙 기록과 시간 범위가 겹치는 부분을 구별한다. 외부 동시 호출량을 상한으로 제한할 수 없으면 50회 여유만 믿고 자동 생성하지 않는다.

안전 여유는 조정 가능한 정책값이다. 처음부터 정확히 500회를 소진하도록 설정하지 않는 이유는 통계 지연·기존 호출 누락·외부 사용·불확실한 전송을 감안하기 위해서다. 사용하지 않은 특정 기능의 배정량은 공통 풀에 남겨 다른 필요한 기능이 활용한다. 새 키·프로젝트·유료 등급을 만들지 않는다.

11.3 모든 HTTP 시도 전에 원자적 예약
callGeminiJson, callGeminiChat, 도구 호출 후 다음 모델 응답, 이미지 입력, 분석, 재생성, 재시도, 예비 모델까지 공통 gate를 거친다. production 여부로 gate를 우회하지 않는다. 단위 테스트는 fake transport/DB를 주입하며 실제 네트워크는 차단한다.

예약 트랜잭션:
1) DB 시각으로 KST 일자·Google 일자·최근 60초 구간을 계산.
2) 프로젝트·모델·기능 정책과 상태를 확인.
3) 정해진 순서로 예산 row를 잠그고 요청량·토큰량·동시성·차단 상태 검사.
4) 공통 잔여 예산·기능 우선순위 보존량·모델 RPD·최근 60초 RPM/TPM·프로젝트 여유를 함께 예약.
5) attempt_id를 기록하고 commit. 하나라도 부족하면 모두 예약하지 않고 호출하지 않음.
6) 예약 성공 후 실제 API를 호출. 응답 실패·timeout·연결 불명도 소비한 요청으로 유지.
7) 완료 결과·모델·응답 상태를 기록하고 동시성 lease 해제. 재시도는 새 attempt를 예약.

분당 한도는 시계의 분 경계가 아닌 직전 60초 sliding window다. 손상된 카운터를 0으로 해석하지 않는다. 예약 후 프로세스가 죽어 실제 전송 여부가 불명확하면 슬롯은 되돌리지 않는다. 일별 카운터를 OFF/ON이나 재시작으로 초기화하지 않는다.

예약과 전송 사이 지연도 다음처럼 다룬다.
• 멀리 미래의 작업은 실행 job만 예약하고 API 사용 permit은 실제 전송 직전에 발급한다.
• permit은 발급 후 2초 안에 같은 worker가 한 번만 사용한다. DB에서 reserved→dispatching CAS를 통과해야 하며, fetch 직전에 deadline·run revision·기능 스위치를 다시 검사한다. 오래된 worker는 permit을 재사용하지 못한다.
• permit 만료 또는 날짜 경계 통과 시 기존 예약 소비량은 보존하고 새 날짜/구간에 새 permit을 받아야 한다. 기존 예약을 새 worker가 승계해 전송하지 않는다. KST/Google 자정 직전 5초에는 신규 자동 전송을 보류한다.
• RPM/TPM 판정에는 최근 완료 전송뿐 아니라 발급된 모든 미완료 permit과 dispatching 시도도 포함한다. rolling 보존 종료는 가장 늦게 전송됐을 수 있는 시각에 네트워크 timeout과 60초를 더해 보수적으로 잡는다. 예약 시각만 기준으로 슬롯을 일찍 해제하지 않는다.
• 전송 결과가 불명확하면 동일 attempt를 재발송하지 않는다. timeout/worker 소실은 uncertain으로 남기고 자동 AI를 정지한 뒤 사용량을 재확인한다. 전송되지 않았다고 추측해 새 호출을 이어가지 않는다.
• DB 트랜잭션과 외부 HTTP는 하나의 원자적 트랜잭션으로 묶을 수 없다. 따라서 확인되지 않은 호출을 버리지 않는 보수적 소비 정책을 사용한다. 공급자 수신 시점·외부 호출을 완전히 통제한다고 보장하지 않는다.

11.4 공통 예산과 필요한 AI의 우선 배분
주 모델의 전체 기능 운영 상한은 Google 집계일 기준 450회다. 자동 기능 150회, 질문 110회, 답변 40회, 비서 100회라는 고정 구획은 폐기한다. 이미 소비한 양과 앞으로 필요한 최소량을 한 번의 원자적 예약에서 검사하여 남은 예산을 활용한다.

AI를 쓰는 일:
• 현재 카드의 실제 상품 정보를 바탕으로 적절한 질문 의도와 자연스러운 문장 생성.
• 인간이 직접 말을 걸었을 때 문맥·의도·응답 가능 여부 분석과 답변 생성. 한 번의 요청으로 처리.
• 기존 AI 비서의 복잡한 문의 해석·정보 정리 등 실제로 필요한 기능.
• 모델 출력의 구조화 검증은 서버에서 하고, 재생성이 꼭 필요한 경우에만 새로운 예산을 소비.

서버가 계산하는 일:
현재 한국 시간, 실제 방송 상태, 상품 ID·가격·옵션 조회, 주문 제출 여부, 시청자 수, 입퇴장·체류, 닉네임 생성, 단순 인사·주문 문구 선택. 이 결과는 AI의 문맥 입력에 포함한다. 사실 확인을 생략하는 것이 아니라 확정된 사실 위에서 AI가 의도와 문장을 판단하도록 나눈다.

공통 풀 운영 규칙:
• 상품 질문은 유효한 주문 슬롯당 생성 1회 이하이며 모든 상품 질문을 주문에 연결한다. 주문 OFF·목표 소진·슬롯 부족이면 생성하지 않는다. 한도를 채우기 위해 불필요한 질문을 만들지 않는다.
• 직접 언급 응답은 9.3의 중복/인물별 제한과 전체 최소 2분 간격을 적용한다. 하루 40회를 넘었다는 이유만으로 남은 공통 예산이 있는데 중단하지 않는다.
• 인사·닉네임·이모티콘·기본 주문 문구는 AI 0회. 재시도와 예비 모델 호출도 실제 시도별 해당 모델 예산을 소비한다.
• 공통 한도에 가까워지면 자동 기능 안에서는 카드 상품 질문을 직접 답변보다 우선한다. 질문 가능한 LIVE+카드 상태에서 향후 30분 예정 주문 질문 수 Q(0~6)를 DB의 전역 주문 스케줄로 계산해 일일 잔여량 Q회와 RPM 1자리·질문 TPM 1회분을 보호한다. 낮은 우선순위 답변은 이를 침범하지 못한다. 예정 질문이 없으면 보호량도 0이다.
• 관리자가 최근 15분 안에 비서를 사용 중이면 다음 비서 요청을 위한 보존량 A=min(10, 공통 잔여량)를 둔다. 자동 기능은 A를 남기고 사용한다. 비서를 15분 이상 사용하지 않았고 대기 요청도 없으면 A=0으로 해제한다. 사용하지 않는 비서 몫을 하루 종일 잠가 두지 않는다. 비서는 자기 보존량을 사용할 수 있으며 모든 기능은 공통 상한을 준수한다.
• 위 보존량은 실제 호출로 차감한 것이 아니라 다른 종류의 요청 허용 여부를 계산하는 보호선이다. Q와 A를 함수별 기준에 맞게 합산하며 실제 예약 원장과 이중 계수하지 않는다. 예산 보호량이 잔여량보다 크면 자동 작업을 생략한다.
• 같은 종류의 자동 작업은 actor별 순환으로 처리해 한 닉네임이 예산을 독점하지 못하게 한다. 개인정보·운영 정책 질문 등 응답하면 안 되는 내용은 예산이 남아도 답하지 않는다.

배분 예: 같은 Google 집계일에 기존 비서 등 다른 기능이 100회 사용했고 외부 offset·다른 소비가 없다면, 450회 운영 상한에서 남은 350회를 필요한 자동 질문·답변에 사용할 수 있다. 이것은 고정 배분이 아닌 실제 소비량에 따른 예다.
8시간에 주문 간격이 5~10분이면 주문은 대략 48~96건, 평균 간격 7.5분이면 약 64건이다. 주문당 질문을 한 번씩 생성한다고 해도 질문만으로 450회를 소진할 필요는 없다. 남은 양은 필요한 직접 응답·비서 작업에 사용한다. 현재 코드에서는 재시도 때문에 실제 HTTP 횟수가 더 많을 수 있으므로 새 gate에서 시도 단위로 확인한다.

예비 모델은 각각의 무료 RPM/TPM/RPD를 확인한 후 모델별 gate를 별도로 적용한다. 3.1은 주 모델 장애 시 제한적 대체 후보, 3.8은 별도 필요가 확인된 작업에만 사용한다. 단순히 하루 500회를 더 채우기 위한 순환 사용은 하지 않으며 quota 429를 다른 모델로 우회하지 않는다. 예비 사용 횟수도 관리자에서 별도로 보여준다.

KST 오늘 사용량은 운영자가 읽는 통계이고, 실제 일일 허용 판정은 Google 일자별 모델·프로젝트 한도를 기준으로 한다. KST 자정이 Google 예산을 초기화하지 않는다. DST는 시간대 라이브러리로 처리한다. 날짜 변경 시 과거 원장을 지우지 않는다.

11.5 토큰·재시도·중단
입력 길이·문맥 개수·출력 토큰을 제한한다. TPM은 요청 전에 입력 토큰의 검증 가능한 상한을 예약한다. 출력 토큰 등 제공자가 별도로 적용하는 제한도 해당 모델 정책대로 예약한다.
기본 자동 질문은 텍스트만 사용하고 생성 요청은 주문당 최대 1회다. 호환성이 검증된 로컬 토큰 계산/보수적 상한을 확보하지 못하면 해당 입력 유형의 AI를 중단한다. 이미지·복잡한 도구 입력은 기존 비서라도 토큰 예약 방법이 확인된 유형만 허용한다. 토큰 계산을 위해 별도 Google API가 필요한 경우 그 요청도 중앙 관리와 동일 자동 예산에 포함하며, 기본 질문 1회 정책을 깨는 숨은 호출로 추가하지 않는다.

자동 질문은 즉시 재시도·자동 예비 모델 전환을 기본 OFF로 둔다. 질문 실패 시 주문만 진행한다. 다른 기능의 재시도는 최대 1회이며 검증된 무료 모델과 새 예약이 있어야 가능하다. 같은 질문에 분석 1회·문장 1회를 따로 호출하지 않는다.

429는 응답의 quota metric·retry delay를 구조적으로 분류한다.
• 분당 한도: 신규 해당 AI를 중지하고 최소 provider retry delay 적용. 자동 채팅은 30분 보호 대기 후 재평가.
• 일일 한도: 해당 Google quota day가 끝날 때까지 차단. KST 날짜 변경만으로 해제하지 않음. 같은 한도 기간에 예비 모델로 우회하지 않음.
• 분류 불가: 일일 한도와 동일하게 보수적으로 중단하거나 관리자 재검증까지 유지.
• 400 설정 오류, 404 모델 오류: 해당 모델 비활성화. 여러 설정·모델을 돌며 연속 호출하지 않음.
• 5xx/timeout: 자동 질문은 생략. 기존 비서 재시도도 새 예약과 상한 내에서만.

11.6 카운터 이전과 관리자 표시
기존 gemini_quota_v1·auto_test_order_v1의 오늘 사용량을 누락하지 않는다. AI를 잠시 정지하고 기존 값, 도입 전 사용량, AI Studio 누적값을 대조해 시작 offset을 설정한다. 중복 여부가 불명확하면 낮게 잡지 않는다. 제공자 사용량을 확정할 수 없으면 다음 공급자 리셋 후 정책 확인까지 AI를 중단한다.

기존 AI 표시 영역을 유지하되 고정 N/150 문구를 바꾼다.
• ‘3.5 Lite 앱 사용 N회 · 운영 상한 450 / 제공자 한도 500 · 사용 가능 R회’는 Google 집계일 기준 모든 앱 기능의 소비와 제한을 표시한다. 도입 전/외부 사용 offset은 별도 상세 항목으로 보여준다.
• ‘한국 시간 오늘 자동 A회 / 비서 B회’는 별도 통계로 구분하며 KST 분자를 Google 일일 한도 분모와 섞지 않는다.
• 질문/답변/비서/재시도별 소비, 예비 모델별 소비, 현재 모델, 제한 이유, 다음 재평가 시각은 기존 접힌 상세 영역에 둔다.
N은 소비한 예약 횟수이며 응답 실패·전송 불명도 포함한다. R은 외부 offset·진행 중 예약 등을 포함한 보수적 잔여량이지 Google의 실시간 원본 사용량이라고 표시하지 않는다. 카운터를 못 읽으면 ‘0’이 아니라 ‘확인 필요’다.
기존 150회 카운터는 이전 자료로 보존한다. 설계 변경만으로 값을 초기화하거나 운영 상한을 실제로 변경하지 않는다.


12. ON/OFF와 종료 처리

주문 ON, 채팅 ON, 접속 ON의 3개 boolean을 각각 저장한다. 신규 설치 기본값은 모두 OFF, 특히 채팅 기본 OFF다. 배포만으로 기존 실행을 새 구조에서 자동 재개하지 않는다.

설정 화면이 여러 개 열려 있어도 각 화면은 작업을 실행하지 않고 서버 설정만 변경한다. 갱신은 version/CAS로 보호한다. stale 요청은 다시 읽게 하고 최신 상태를 덮어쓰지 않는다.

스위치 조합:
• 주문 ON / 채팅 OFF / 접속 OFF: 주문만 실제 제출, 시청자 인원 변화 없음.
• 주문 OFF / 채팅 ON / 접속 OFF: 채팅만 실행, 시청자 수를 채팅 때문에 늘리지 않음.
• 주문 OFF / 채팅 OFF / 접속 ON: 입장·체류·퇴장만 실행.
• 모두 ON: 같은 actor/session으로 세 흐름을 연결.
• AI 한도 도달: AI 생성만 생략. 주문·접속·허용된 서버 문장·삭제 기능 유지. 관리자에 AI 제한 상태 표시.
• 전체 종료: 새 작업 claim 차단 → 진행 중 결과 확인 → 시청 종료·토큰 폐기 → 자동 장바구니 해제 → 공개 자동 메시지 숨김 → 캐시·실시간 갱신 → 자동 활성 인원 0 검증.

OFF가 저장되기 전에 이미 제출된 주문은 취소하지 않는다. 주문 저장 트랜잭션은 campaign → run → actor → action 순서로 row를 잠그고 반복 작업의 orders_enabled, run.status=running, (ends_at IS NULL 또는 DB now<ends_at), 현재 config_revision, claim 소유자와 fencing_version을 모두 검사한다. 같은 트랜잭션에서 actor의 목표 잔여 수, 닉네임 snapshot, 전역 주문 슬롯, 유일 idempotency key를 검사하고 주문 저장·성공 연결·다음 슬롯 확정을 함께 commit한다. 종료/스위치 변경도 같은 잠금 순서를 사용한다. 종료가 먼저 commit되면 늦은 주문 저장을 거부하고, 주문 저장이 먼저 commit되면 그 주문은 이미 제출된 결과로 보존한다.

채팅 insert도 chat_enabled와 같은 종료·revision·fencing 조건을 저장 경계에서 검사한다. presence의 leave_at/종료 session도 heartbeat 저장 경계에서 검사한다. worker의 실행 직전 검사만으로 대신하지 않는다. 네트워크로 이미 발송된 Gemini 요청은 취소를 시도하더라도 사용량을 되돌리지 않는다.

반복 조작 규칙: 기능 ON이면 해당 작업만 새로 예약한다. OFF 때 취소된 질문/주문을 다시 켠다는 이유로 늦게 제출하지 않는다. 같은 방송의 새 run은 campaign의 인물·말투·누적 주문 수·전역 다음 주문 가능 시각을 이어받고, 시청 세션만 새로 만든다. 재ON 시 과거 due 작업을 한꺼번에 실행하지 않는다. 재개 후 첫 자동 제출은 max(현재 시각, 마지막 실제 제출 시각)에서 5~10분 뒤로 새로 예약하며 누적 수는 초기화하지 않는다. 종료된 세션을 부활시키지 않는다. 이미 완료한 주문과 AI 소비량은 유지한다. 사이트 방송 종료는 모든 기능과 scheduler를 끄며, ‘잠시 쉬는 중’은 방송 종료가 아니다. PAUSED에서는 인사·접속·현재 판매 가능한 상품의 주문을 스위치대로 유지하되 라이브 상품 AI 질문은 중지한다. ‘다시 시작’은 방송 상태만 바꾸고 꺼져 있던 자동 기능을 켜지 않는다.

‘지금 테스트’는 기존 의도를 유지하는 일회 실행이다. 누르면 실제 주문서 1건을 제출하며 반복 스위치를 자동 ON으로 바꾸지 않는다. 화면 클릭까지 수행하는지는 연결된 실행호스트 유무에 따른다. 채팅/접속 OFF도 몰래 켜지 않는다. 한 번에 1~3건을 몰아 제출하는 버튼이 아니다. 반복 주문 OFF일 때도 관리자 명시 클릭으로 1건은 허용하되, 일회 action에만 적용되는 서버 발급 권한과 idempotency key를 사용한다. run이 stopped인 상태를 일반 worker가 우회하는 대신 짧은 manual run을 만들고 종료한다. 같은 campaign의 주문 목표가 남은 인물 또는 새 인물에 연결하고 누적 수를 보존한다.

브라우저 실행 계약: 일반 사이트 자바스크립트가 Playwright의 격리 context를 직접 만들 수 있다고 가정하지 않는다. 기본 일회 실행은 기존 일반 주문 API를 통해 실제 주문서 1건을 제출하고 결과는 ‘주문서 제출 확인’으로만 표시한다. 개발/운영 확인 때 인증된 로컬 실행호스트가 연결돼 있으면 해당 action을 독점 claim하여 격리 브라우저에서 실제 상품 선택·주문 버튼을 실행할 수 있다. 이 호스트는 필요할 때만 켜며 Vercel에 상시 브라우저를 띄우지 않는다. 호스트에 무제한 서비스 키를 전달하지 않고 한 run/action으로 제한한 단기 교환 권한만 준다.

호스트가 claim하기 전에 연결 불가가 확정된 경우에만 server driver를 선택한다. claim 이후 연결이 끊기면 같은 idempotency key의 저장 여부를 조회해 해결하고, 불명확하면 uncertain으로 정지한다. 다른 driver가 새 키로 대신 제출하지 않는다. 결과에는 driver와 실제 클릭 증거 유무를 내부 저장한다. 서버 제출 결과를 ‘화면 클릭 검증 완료’라고 표시하지 않는다. 초기 구현 검증에서는 일반 관찰용/주문용 실제 context 2개로 UI·영상·저장소 격리를 별도로 확인한다. 기존 화면 주문 기능은 호스트 연결 시 유지하되 고객 localStorage 임시 교체는 재사용하지 않는다.

일회 실행은 주문 스위치만 예외로 허용하며 다른 권한·상품 검증·금전 보호·정지 epoch는 동일하다. 채팅 ON일 때도 일회 화면 동작의 선행 상품 질문은 생략하고 검증된 인사/제출 확인만 허용한다. 따라서 질문 후 30~120초 예약과 충돌하지 않는다. 전역 주문 잠금으로 예약 반복과 수동 실행이 동시에 제출되지 않게 한다. 수동 클릭은 사용자가 요청한 즉시 1건이며 자동 5~10분 간격 검증과 구분한다. 수동 성공 시각 이후 다음 자동 주문을 다시 5~10분 뒤로 잡는다. 이미 질문을 게시한 자동 주문 대기 중에는 수동 버튼을 ‘질문 주문 대기’로 잠깐 비활성화해 그 연결과 시간 약속을 깨지 않는다. UI뿐 아니라 서버 claim 경계에서도 같은 조건으로 수동 실행을 거부한다.

일회 진행 중 버튼은 ‘중지’로 전환해 미제출 작업을 취소할 수 있다. 중복 클릭은 같은 action 상태만 돌려주며 여러 관리자도 campaign당 일회 실행 하나만 허용한다. 주문 스위치 OFF 전환·일회 중지·방송 종료는 진행 중 일회 action에도 cancellation epoch를 올려 미제출 저장을 막는다. 이미 저장된 주문은 보존한다. 완료/취소 시 임시 세션과 전용 scheduler를 정리하고 기존 ON 기능만 남긴다.

전체 종료 후 저장 주문은 검토를 위해 남기며 삭제 버튼으로 별도 정리한다. heartbeat를 받지 못한 세션도 read-time 만료 조건으로 즉시 유효 인원에서 제외한다. 마지막 작업이 실패해도 공개 숫자가 계속 남는 구조를 만들지 않는다.


13. 첨부 화면을 기준으로 유지할 UI/UX

13.1 관리자 방송 카드
첨부한 카드의 ‘잠시 쉬는 중’, 경과 시간, 방송명, 검은 ‘다시 시작’, ‘방송 종료/방송 관리’, 구분선과 자동 기능 영역의 순서를 유지한다. 자동 기능 때문에 새 대시보드나 별도 실행 페이지로 이동하게 만들지 않는다.

자동 영역의 기본 순서:
  자동 테스트 주문      [스위치]
  꺼짐 / 켜짐 · 다음 16:10쯤 / 멈추는 중
  자동 테스트 채팅      [스위치]
  꺼짐 / 켜짐 / AI 생성 쉬는 중
  자동 테스트 시청자    [스위치]
  꺼짐 / 접속 중 N명 / 멈추는 중
  마지막 결과 한 줄
  [지금 테스트]         [기존 주문 삭제]
  손님 화면으로 보기
  접힌 상세 정보

앞 두 스위치와 지금 테스트/삭제 위치는 기존 구조를 유지하고 시청자 행 하나만 같은 패턴으로 추가한다. 현재 소스의 ‘손님 화면에도 보이기’는 실행자에게 또 설정하게 하지 않고 활성 실행의 일반 화면 반영 정책으로 통합한다. 이 스위치를 시청자 스위치로 단순 이름 변경해 기존 publicTest 값이 viewers_enabled가 되는 마이그레이션은 금지한다. 새 시청자 값은 OFF에서 시작한다. 고객 확인 링크는 ‘손님 화면으로 보기’로 정리하고 일반 회원과 같은 공개 경로를 사용한다. ‘테스트 글 포함’ 전용 조회 우회로만 확인해서 정상이라고 판정하지 않는다.

지금 테스트는 평소 기존 문구, 준비/실행 중에는 진행 상태와 ‘중지’, 정리 중에는 ‘정리 중…’으로 표시한다. 전송 버튼 연타를 막되 중지 조작까지 막지 않는다. 기존 삭제 버튼은 생성한 주문이 있을 때만 노출하고 영구 삭제 확인을 유지한다. ON/OFF에는 불필요한 확인 팝업을 추가하지 않는다.

13.2 상태와 접근성
기존 bg-ink/bg-line/bg-surface/text-ink/text-ink-mute/border-line 토큰과 Switch 컴포넌트를 재사용한다. 현재 스위치의 h-7 w-12 외형, 제목 13px/설명 12px, 버튼 h-9, 카드의 간격/라운드를 유지하되 행의 클릭 영역은 최소 44px로 확보한다. 새 컬러·아이콘 체계를 만들지 않는다. role=switch, aria-checked, 키보드 포커스, 로딩/비활성 상태를 제공하며 색만으로 켜짐/꺼짐을 구별하지 않는다.

저장 중에는 ‘변경 중’, 서버 저장 실패는 이전 확정 상태와 간단한 오류를 표시한다. OFF 트랜잭션이 끝나면 ‘멈추는 중’으로 이미 나간 요청의 정리 결과를 확인하고, 반복 예약 비활성·활성 자동 인원 종료가 확인돼야 ‘꺼짐’으로 확정한다. 지연되면 ‘중지 확인 필요’로 표시하며 성공으로 덮지 않는다. 새로고침과 다른 관리자 창은 서버 상태를 다시 읽는다. 일반 설정 GET이 멈춘 전체 OFF 상태에서도 직접 ON 조작은 작동한다.

마지막 결과는 ‘16:10 주문서 제출 확인’, ‘16:12 구매 가능한 상품 없어 건너뜀’처럼 실제 결과 한 줄만 보인다. 품절 건너뜀을 빨간 ‘주문 실패’나 실패 주문서로 만들지 않는다. 상세 접힘에는 실접속/자동접속/화면 합계, 기능 상태, 필요 시 종료 시각, AI 모델별 소비/운영 상한/잔여만 둔다. 나이·성별·프롬프트·cron 용어·별도 복잡한 로그 페이지는 기본 운영 화면에 추가하지 않는다.

13.3 일반 회원과 실제 방송 노출
기존 눈 숫자·사이트 숫자·닉네임·첫 글자 원형 프로필·채팅·상품 카드·주문 흐름을 유지한다. 활성 실행의 유효 접속은 일반 회원에게도 같은 집계 결과로 보이며, 채팅/주문 행에 (테스트)/[TEST]/AI 등 접두어·배지를 추가하지 않는다. 내부 provenance·안전 삭제 필터는 유지한다.

테스트 제어 문구는 인증된 관리자 설정 카드에만 존재한다. 실제 방송에 노출되는 채팅 뷰어·OBS 소스·고객 화면·주문 화면에 관리자 제어 카드·진행 토스트·자동화 도구 화면이 함께 나오지 않게 렌더링 경계를 분리한다. 관리자 전체 화면을 외부 방송으로 캡처하면 제어 문구도 보일 수 있으므로 구현 검증은 실제 사용하는 방송 소스를 기준으로 한다. 격리 브라우저의 자동 조작 상태를 고객 페이지에 오버레이하지 않는다.

모바일/PC의 서로 다른 일반 회원 context에서 숫자가 같은 서버 집계로 수렴하는지 확인한다. UI 표식 제거 자체를 자연스러운 말투의 증거로 삼지 않고 9장의 대화 품질을 따로 검증한다.

13.4 과거 메시지
새 메시지는 서버가 검증한 actor/session provenance를 사용한다. 과거 autotest 표식·전용 customer ID·kakao_id·주문 연결을 근거로 확정된 것만 내부 자동 메시지로 분류한다. 같은 닉네임의 일반 고객 발언은 변경하지 않는다. 연결이 모호한 과거 메시지에는 세션을 추정해서 붙이지 않고 legacy로 남긴다.

14. 기존 기능 보호와 배포 순서

14.1 수정 대상의 범위
• lib/autoTestOrder.ts, autoTestOrderServer.ts: 공유 닉네임 변경 제거, session 연결, job/idempotency, 상품 snapshot과 스위치 분리.
• lib/autoTestViewers.ts: 별도 배열 인원 합산 제거, 실제 presence 기반 실행·만료로 교체.

• lib/autoTestChat.ts, geminiJson.ts, geminiGate.ts: 시간·상품·방송 검증, 직접 언급 응답, 원자적 공통 예산.
• app/api/live-chat, cart-reservations, customer-orders/submit: 검증된 automation context 전달, 소유권·idempotency·부수 효과 차단.
• ScreenTestHost와 관련 관리자 설정/일반회원 채팅·시청자 컴포넌트: 격리 실행, 공개 표시 정책, 설정 컨트롤.
• SQL migration: 실행·campaign·인물별 주문 목표·세션·작업·AI 예산 구조, FK/UNIQUE/인덱스/RLS, ON/OFF와 예약 활성의 원자적 갱신, 기존 데이터 연결.
• vercel.json 및 기존 자동 cron route: 자동 주문용 매분 예약 제거·구형 실행 진입 차단. 다른 업무 cron 유지.
• components/admin-live/AutoTestOrderSettings.tsx: 기존 Switch/카드 재사용, 시청자 분리, 일회 중지, OFF 폴링 종료, publicTest 표시 정책 통합.
• 결제·포인트·재고·정산·배송·봇 발송의 기존 진입점: 자동 context 차단 여부를 점검하고 누락된 경계만 보완.
새 파일 이름·기존 모듈 분할은 구현자가 정하되 기존 고객 경로의 동작 변경을 최소화한다.

14.2 적용 단계
1) 최신 원격·배포 커밋·DB 재확인. 다른 작업의 미커밋 변경은 보존.
2) 읽기 조사 결과와 스키마를 고정해 재현 테스트 작성.
3) AI gate부터 로컬/격리 데이터로 검증. 실제 모델 호출 없이 한도·동시성·오류 경계 테스트.
4) additive migration으로 새 구조와 nullable 연결 칸 추가. 기존 고객 경로 호환 유지.
5) 자동 실행을 정지하고 진행 중 주문 결과를 확정한 뒤 기존 실행 상태를 이관. AI 카운터는 보존.
6) 과거 데이터는 확실한 내부 ID로만 backfill. 이전 가상 시청자 배열은 읽기 자료로 남기고 새로운 활성 세션으로 승격하지 않음.
7) 새 서버 실행기를 연결하되 기본 OFF. 기존 실행기와 동시 동작 방지.
8) 고객 기능 회귀·권한·금전 제외·스위치 검증 후 코드 배포.
9) 운영 화면에서 1→3→5세션과 5~120분 체류, 실제 주문서 경로 검증.
10) 종료·일반 고객 데이터 무영향·공개 자동 인원 0 확인 후 결과 보고.

Gemini 정책 확인이 끝나지 않아도 접속·주문·서버 문장 검증은 먼저 할 수 있다. 공급자 한도를 실제로 초과시키는 실험은 하지 않는다.

14.3 되돌리기
새 실행을 중지하고 토큰/활성 세션을 종료한다. 공개 합산을 해제하고 기존 고객 UI·API를 유지한다. 추가 컬럼·연결 기록은 남겨 원인 확인과 주문 보호에 사용한다. 오래된 실행기나 제한이 약한 Gemini 코드로 자동 복귀하지 않는다. 안전한 버전으로 되돌리기 전까지 자동 기능은 OFF를 유지한다.


15. 실행에서 수집할 증거

• 실행 전후 회원 행 수, 자동 actor/session 수, 활성 인원.
• 일반 화면의 숫자와 같은 시각 서버 집계, join/heartbeat/leave 요청 ID.
• 저장된 주문서 ID, 요청 idempotency key, 질문 메시지 ID, 상품 snapshot 비교.
• 실제 브라우저의 클릭·화면·응답 상태, 영상 재생 여부.
• 금전·재고·포인트·입금·배송 데이터의 전후 비교. 다른 정상 거래가 동시에 있으면 단순 총합 대신 해당 run의 변경 경로와 대상 행으로 비교.
• AI 예약·전송·실패·모델·기능별 소비량. 프롬프트의 개인정보·키는 로그에 남기지 않음.
• 요청 수·오류율·p95·실행 장치 CPU/메모리·DB/함수 사용량.

heartbeat마다 대용량 로그를 영구 저장하지 않는다. 세션 현재 상태와 join/leave/error 요약만 보존하며 상세 요청 증거는 실행 결과 파일에 수집한다. 초기 제안 보존기간은 작업 상세 7일, 집계/AI 예약 30일이다. 기존 개인정보 보존정책이 더 짧으면 그 기준을 따르고 현재 quota day의 안전 카운터는 조기 삭제하지 않는다.


16. 검증 방식과 완료 조건

단위·통합 검증은 가짜 시계와 격리 DB를 사용해 120분·자정·DST·동시 요청·재시작·OFF 경계를 빠르게 확인한다. 이것을 실제 2시간 체류 관찰로 바꾸어 보고하지 않는다. 실제 방송에 연결한 2시간 체류 확인은 별도로 수행하고 소요 시간을 기록한다.

실제 브라우저는 페이지 요청을 mock으로 대체하지 않고 사이트의 운영 경로를 사용한다. 생성한 주문만 내부 제외 플래그가 적용되는지 확인한다. 브라우저 없이 보낸 API 요청은 화면 클릭 검증과 구별해 보고한다.

완료 조건은 핵심 기능 31개와 추가 경계 검증을 통과하고, 자동 활성 인원 0·실제 고객 데이터 보호·공개 화면 원복을 확인한 것이다. 총 46개 검증 항목의 근거를 남긴다. 공급자 할당량을 확인하지 못한 상태에서는 ‘AI 제외 기능 검증 완료, AI 정책 확인 대기’로 보고하며 전체 완료라고 표현하지 않는다.


17. 최초 요청의 31개 검증 항목 대응표

01 계정 총개수
   실행 전후 자동 customer=1, operator 등록 수 불변. DB 조회 증거.
02 닉네임별 회원 생성 여부
   actor는 증가해도 customers 신규 생성 없음. DB 차이 확인.
03 닉네임·주문·채팅 연결
   actor/session/customer와 nickname_snapshot 대조. 과거 legacy는 별도 표시.
04 관리자 채팅 표시
   최신 지시에 따라 화면 접두어 없이 표시. 내부 자동 식별과 일반 고객 오분류 0 확인.
05 첫 글자 프로필
   한글·영문·숫자·emoji/결합문자 및 닉네임 변경 검증.
06 A 입장
   실제 join API 성공 후 일반/관리자 화면 20초 이내 증가.
07 B·C 입장
   고유 session별 1명씩 증가. 기존 인원 기준과 함께 기록.
08 동시 접속
   겹친 heartbeat·중복 요청에도 session당 1명. 공유 계정 때문에 합쳐지지 않음.
09 랜덤 체류 종료
   정확한 다섯 시간 중 선택, 서버 due/leave_at 검증. 실제 120분 별도 관찰.
10 퇴장 감소
   정상 leave, 강제 종료, 네트워크 끊김 각각 정상 감소.
11 닉네임 변경
   접속 수·입장·퇴장 예정 불변, 새 메시지 이름만 변경.
12 현재 카드 질문
   실제 카드 ID·revision과 질문 일치. 카드 없음·변경 경계에서 발송 차단.
13 질문 후 동일 상품 주문
   저장된 질문 ID와 30~120초 제출 시각, 주문 내 상품 ID 일치.
14 관리자 주문 표시
   기존 주문 목록에 실제 저장·실시간 등장. 최신 지시에 따라 접두어 없음, 내부 분류 유지.
15 영구 삭제
   생성한 주문 개별·일괄 삭제와 관련 데이터 정리. 재시도로 부활하지 않음.
16 일반 주문 보호
   격리 DB에서 혼합 주문서 삭제 거부. 운영 일반 주문에 삭제 요청을 보내 검증하지 않음.
17 한국 시간 인사
   04:59/05:00, 10:59/11:00, 16:59/17:00, 20:59/21:00 및 생성/전송 시각 경계.
18 방송 모드
   LIVE/PAUSED/REPLAY/ENDED/UNKNOWN별 허용 동작과 늦은 상태 응답.
19 직접 언급 응답
   인간 reply/mention만, actor끼리 루프 없음, 원문별 최대 1답변, 운영 문의 임의 답변 없음.
20 Gemini RPM
   최근 60초 경계·동시 요청·재시도 포함. 실제 provider를 한도 초과 호출하지 않음.
21 모델 RPD
   모델별·프로젝트 공유와 Google 자정/DST 검증.
22 공통 예산 동적 배분
   주 모델 449회에서 동시 요청을 보내 운영 상한 450 내 하나만 예약. 자동 사용 150회를 넘어도 공통 잔여가 있으면 허용. 비서·답변·질문 보호량 해제/회수와 실패·예비 모델별 소비 검증.
23 중앙 통제
   직접 네트워크 호출 정적 탐색 + fake transport 계측으로 JSON/chat/tools/비서 모두 gate 통과.
24 AI 한도 도달
   추가 생성 HTTP 0회. 관리자 제한 상태와 카운터 일치.
25 AI 중단 중 주문·접속
   Gemini를 강제로 사용할 수 없는 상태에서 실제 주문서 제출·입퇴장 정상.
26 재시작 후 카운터
   서버 종료·재시작·설정 OFF/ON에도 소비량 감소 없음.
27 다중 인스턴스
   독립 worker 동시 예약·claim, 중복 주문·채팅·인원·AI 초과 0.
28 기존 비서와 충돌
   비서/자동 기능 동시 요청에 공통 무료 상한 적용, 기능별 예산 표시.
29 세 스위치
   8가지 조합 및 실행 도중 OFF, 지연 요청, stale 설정 갱신 검증.
30 종료 후 인원
   생성한 유효 시청 세션 0, 공개 숫자는 남은 실제 접속만, 예약도 종료.
31 기존 고객 영향
