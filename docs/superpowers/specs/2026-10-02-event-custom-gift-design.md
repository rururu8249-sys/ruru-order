# 이벤트 직접입력 경품 자동등록 및 지급 실패·동시 실행 검증 설계

## 1. 사용자 의도와 성공 기준

운영자가 이벤트 보상을 포인트 대신 직접입력으로 선택하면, 입력한 경품명을 실제 당첨자의 해당 방송 최신 유효 주문서에 상품 한 줄로 자동 추가한다. 상품명은 입력한 값, 수량 1, 단가·상품금액·배송비·카드추가금·포인트사용액 모두 0, 색상·사이즈 없음. 당첨자 여러 명이면 각 사람에게 한 줄씩 추가한다.

고객 주문 조회, 관리자 주문 상세, 상품별·고객별 물건챙김에서 동일한 줄이 보인다. 기존 주문의 금액·결제 상태·주소는 변경하지 않는다. 새 줄은 안 챙김으로 시작하므로 기존 주문이 전부 챙김이었어도 경품 누락을 숨기지 않는다.

추가 검증은 기존 금융 성공 검사뿐 아니라 실제 처리 단계 실패, 응답 유실 후 재시도, 관리자 동시 실행, 잔액과 이력의 일관성까지 포함한다. 실제 고객에게 장애를 주입하거나 테스트 포인트를 지급하지 않는다.

## 2. 읽기 전용 확인한 현재 구조

운영 프로젝트 rpmpqudiscpasivrwuyz의 테이블·인덱스·함수 메타데이터를 조회했다. 고객 데이터 본문은 조회하지 않았다.

- 주문 상품 줄은 public.orders 행으로 저장된다. orders.order_group_id / order_lookup_code로 주문서를 묶는다. 별도 order_items 테이블/JSON만 변경하면 현재 물건챙김에 연결되지 않을 수 있다.
- orders.id bigint, created_at timestamptz, broadcast_id uuid, customer_id bigint, customer_phone text, picked_at timestamptz가 실재한다. orders에는 payment_status 컬럼이 없다. 존재하지 않는 컬럼을 추가 조회하지 않는다.
- event_roulette_events.broadcast_id는 text이다. orders.broadcast_id와 타입이 다르므로 유효 방송 UUID 검증과 명시적 타입 변환이 필요하다.
- 당첨 행은 event_roulette_winners.id UUID이다. 현재 당첨 행에는 경품 종류·경품 주문 연결·사람별 주문 ID 스냅샷이 없다. 이벤트 쪽에는 participant_snapshot과 첫 당첨자의 winner_order_ids가 있다.
- admin_add_order_item(bigint, bigint, text, text, text, integer, integer, text) 함수가 운영에 존재한다. NULL product_id 직접입력·0원 추가를 지원한다. 새 주문 행에 기준 주문 created_at과 그룹·상태를 복사하고 상품금액만 계산한다.
- 해당 기존 함수는 SECURITY DEFINER이며 현재 PUBLIC/anon/authenticated에도 EXECUTE 권한이 있다. 새 자동 경품 처리에서 이 권한 설정을 복제하지 않는다. 기존 함수의 외부 호출 가능 여부는 별도 보안 검증 항목으로 기록하며, 영향 분석 없이 운영 권한을 갑자기 변경하지 않는다.
- customer_point_ledger_source_key_uidx는 source_key IS NOT NULL 조건의 유니크 인덱스이다. customer_point_balances.customer_phone도 유니크이다.
- 기존 관리자 포인트 API는 잔액 읽기 → 이력 INSERT → 잔액 upsert를 별도 요청으로 수행하고 잔액 실패 시 이력 DELETE로 보상한다. 따라서 유니크 키만으로 원자성·서로 다른 지급의 잔액 누적까지 입증할 수 없다.
- orders 자동적립 트리거는 상태 UPDATE에 연결돼 있다. INSERT 자체에는 운영 메타데이터 조회상 자동적립 트리거가 없다. 그 외 집계·조회 동작은 반드시 별도로 테스트한다.
- 기존 실제 컴포넌트 지급 경계 14개 테스트를 재실행하여 통과했다. 아직 새 경품 등록이나 추가 금융 장애 테스트가 완료된 것은 아니다.

## 3. 접근 비교와 선택

A. 브라우저에서 당첨 후 최신 주문을 조회하고 바로 추가: 구현량은 적지만 창 두 개·새로고침·응답 유실에서 중복과 부분 저장을 막기 어렵다. 사용하지 않는다.

B. 서버가 당첨 행을 기준으로 고객·최신 주문을 확정하고 DB 트랜잭션으로 상품 추가와 처리 기록을 함께 저장: 권장. 기존 주문 상품 모델을 재사용하며 한 당첨 건의 재시도는 같은 결과를 반환한다.

C. 경품 전용 주문을 새로 생성: 원래 고객 주문과 분리되어 물건챙김/배송비/입금매칭을 더 복잡하게 만든다. 사용하지 않는다.

선택 B. 주문·이벤트 인터페이스와 DB 처리 경계를 연결하므로 구조 변경 작업(architectural)으로 진행한다.

## 4. 경품 설정과 당첨 확정

직접입력 이벤트에 한해 생성 시 custom_gift_name을 서버에 저장한다. NULL이면 기존 포인트/구형 동작이며 이 작업에서 변경하지 않는다. 공백만 있는 직접입력 상품명은 시작 전에 막는다. 직접입력은 현재 UI 제한인 40자 안에서 앞뒤 공백만 제거하고 표시 문자열을 보존한다. HTML로 해석하지 않는다. 기존 포인트 자동지급 설정·저장·실행 시점은 변경하지 않는다.

시작할 때의 보상 설정을 고정한다. 추첨 중 입력 필드를 수정하거나 다른 이벤트를 선택해도 이미 시작한 판의 보상이 바뀌지 않는다. 서버 확정 당첨 행마다 소유자 판단용 주문 ID 스냅샷을 저장한다. 클라이언트가 보낸 전화번호나 주문 ID를 그대로 보상 대상으로 신뢰하지 않는다.

기존 결과에는 직접입력 스냅샷이 없으므로 포인트/상품명으로 추정하지 않는다. 이번 배포 이전 당첨 기록에는 자동 경품을 소급 추가하지 않는다. 명시적인 새로운 실행부터 적용한다.

단일·다중 추첨 결과 저장에 같은 이벤트 ID의 동시 확정 방어가 필요하다. 이벤트 행 잠금 및 상태 검사로 이미 확정된 결과를 재사용한다. 동일 eventId의 두 관리자가 다른 당첨 결과/당첨 행을 만들지 않도록 실제 병렬 DB 검사를 넣는다. 서로 다른 새 eventId는 서로 다른 판이며, 자동으로 같은 판이라고 합치지 않는다.

## 5. 고객과 최신 주문서 선택

방송 범위는 날짜·현재 방송 UI 값이 아니라 저장된 event.broadcast_id이다. 자정이나 방송 종료 후에도 다른 방송으로 넘어가지 않는다.

1. 서버가 당첨 행/이벤트/해당 당첨자의 저장된 주문 ID 스냅샷을 조회한다.
2. 해당 방송의 실주문에서 고객을 한 사람으로 확정한다. customer_id가 있으면 검증한 customer_id를 사용한다. 없는 구형 데이터는 정규화 전화번호를 쓰되 후보 고객이 둘 이상이면 중단한다.
3. 같은 닉네임의 다른 고객을 첫 행으로 임의 선택하지 않는다. 수동 참가자도 해당 방송의 주문자 한 사람으로 정확히 확인되는 경우만 가능하다.
4. 삭제·영구삭제·취소·테스트 주문을 제외한다. 취소 판정은 기존 주문 상태 정규화 함수를 재사용한다. 해당 방송의 주문서 제출자 전체도 참가할 수 있으므로 미결제라는 이유만으로 최신 주문을 제외하지 않는다.
5. 최초 정상 처리 요청에서 가장 최근 주문서를 선택한다. 원래 주문 줄 created_at DESC와 원래 주문 줄 id DESC로 순서를 고정하고 기존 경품 줄은 최신 판정에서 제외한다. 동일 그룹의 상품 여러 줄은 한 주문서로 본다.
6. 선택한 주문 기준 행을 잠근 후 고객·방송·삭제·취소 여부를 다시 검사한다. 잠금 대기 중 취소되면 성공으로 처리하지 않는다.
7. 같은 요청을 재시도하면 최초 성공 시 연결한 주문서 결과를 반환한다. 이후 더 최근 주문이 생겨도 경품을 다시 옮기거나 두 번 넣지 않는다.

선택 시점은 해당 처리 트랜잭션의 조회 시점이다. 그 이후 제출되는 새 주문까지 미래의 최신 주문으로 보장할 수는 없다. 성공 후 경품 줄/주문이 삭제·취소되어도 자동 재추가는 하지 않는다. 재시도에 원래 등록 이력과 현재 대상 상태를 알린다.

## 6. 서버 저장 계약과 보안

관리자 세션이 필요한 이벤트 보상 처리 endpoint에서 winnerId만 받고, 상품명·수량·금액·고객·방송은 서버의 저장된 판 설정으로 결정한다. 조회용 위젯이나 iframe callback은 호출하지 않는다.

직접입력 경품 처리 기록은 winnerId당 유니크한 receipt로 저장한다. 대상 주문 줄·그룹, 상품명, 처리 시각을 보존한다. 포인트 ledger와 처리 구조는 변경하지 않는다. 기록은 직원 감사와 재시도용이며 공개 overlay에 고객 ID·전화번호·주문 ID를 추가하지 않는다.

경품 등록, receipt INSERT, 당첨 행 처리 완료 마킹은 한 DB 트랜잭션으로 함께 성공하거나 모두 rollback한다. winnerId 잠금/유니크 receipt가 다른 브라우저·관리자 동시 실행에도 최종 방어한다. 마킹만 성공하고 상품이 없는 상태를 만들지 않는다. 기존 is_reward_done만으로 새 경품 완료를 추정하지 않는다.

새 함수는 SECURITY INVOKER를 기본으로 하고 관리자 서버의 service_role만 EXECUTE 가능하게 한다. PUBLIC/anon/authenticated 실행 권한을 명시적으로 제거한다. 새 테이블은 RLS와 최소 권한을 설정한다. 기존 함수 내부 재사용이 필요하더라도 새 외부 접근 경계는 유지한다.

orders에 경품 origin을 구분할 수 있는 연결 정보를 추가하여 판매 통계·자동 응모권 가중치에서 경품을 구매로 오인하지 않도록 한다. 물건챙김/수량 표시에서는 실제 챙길 한 개로 포함한다. 등록 상품 카탈로그에는 가짜 0원 판매상품을 생성하지 않는다. NULL product_id, 색상·사이즈 NULL, 수량1, 금액 열 모두0, picked_at NULL. 결제 완료 주문의 경품은 결제완료만 필터에서도 보이게 기존 그룹 결제 상태 판정을 검증한다.

기준 주문의 customer/broadcast/group/address 및 필요한 상태·표시 필드를 실재 컬럼 목록으로 복사한다. 계좌 배정과 포인트 사용액을 원래 주문에서 다시 계산하거나 재배정하지 않는다. 새 줄에 중복 배송비/포인트 사용액을 복사하지 않는다.

## 7. 금융 실패·동시 실행 검증과 보완 범위

단순 화면 mock 성공을 DB 동시성 검증으로 보고하지 않는다.

사용자 범위 확인: 이번 새 기능은 직접입력 경품이며 기존 포인트 자동지급은 유지한다. 기존 관리자 지급 API의 분리 저장 구조에 대해 아래 API/DB 검사를 격리 환경에서 수행하지만, 포인트 API·DB 함수·지급 타이밍을 이번 계획에서 교체하지 않는다. 발견된 기존 포인트 결함은 재현 근거와 위험도를 별도 보고하고, 수정 범위 승인을 받기 전에는 변경하지 않는다.

같은 source_key 병렬 요청의 한 번 지급, 다른 source_key 같은 고객 잔액 합산, 저장 실패 후 잔액·이력 일치, 응답 유실 후 재시도를 실제 결과와 대조한다. 기존 분리 저장의 부분 실패가 재현되면 테스트 결과를 실패로 남긴다. 테스트를 통과시키려고 기대값을 낮추거나 결함을 성공으로 간주하지 않는다.

관련 주문 사용/복구·자동적립·미션·수동 지급 등 writer도 격리 환경에서 검사한다. 검증하지 않은 writer까지 안전하다고 주장하지 않는다. 과거 잔액과 이력 차이를 발견해도 운영 잔액을 추정하여 자동 보정하지 않는다.

프런트는 성공 확인 전 완료 표시하지 않는다. 시간초과/응답 유실은 결과 불명 상태로 표시하고 같은 winnerId/source_key로 재확인·재시도한다. 실패한 당첨자는 기록에서 다시 처리할 수 있도록 한다. UI 재연결/애니메이션 완료는 지급의 증거가 아니다.

## 8. 실행 시점·실패·복구 UI

서버 당첨 결과를 정상 저장한 뒤 직접입력 경품을 자동 처리한다. 저장한 직접입력 설정만 사용하고, 기존 포인트 분기에는 새 경품 요청을 보내지 않는다. 경품 처리는 표시 애니메이션/iframe mount/화면 숨김에 의존하지 않는다. 기존 포인트 타이밍은 그대로 유지한다.

새 상태: 주문서에 추가 중 / 주문서에 추가 완료 · 주문번호 / 추가 실패 · 이유 · 재시도 / 결과 확인 필요. 다중 당첨은 사람별 상태 표시, 실패 건만 재시도. 이미 성공한 건은 건너뛴다. 전체 성공 전에 일괄 성공 토스트를 띄우지 않는다.

이벤트·주문 데이터 재조회로 관리자 주문 목록/상세/챙김과 고객 주문 조회가 실제 DB 줄을 읽는다. 두 관리자 창도 재조회 시 동일 상태를 보이며 iframe 미리보기에는 보상 실행 권한을 주지 않는다.

사용자 조작 테스트 외에 서비스 워커/브라우저 강제 종료까지 영구 실행 보장하는 새 큐는 이번에 만들지 않는다. 요청 전 창을 닫으면 자동 처리가 미시작일 수 있으므로 미처리 당첨 기록과 재처리 경로를 제공한다. 요청이 DB에 도달했다면 재시도로 중복 없이 결과를 확인한다.

## 9. 검증 매트릭스

- 서버 계약: 비로그인/잘못된 세션 거부, 존재하지 않는 당첨 ID, 다른 판·방송의 주문, forged 고객/상품/금액, 공백·긴 상품명, HTML 문자열.
- 선택: 같은 고객 주문 3개 → 최신 1개, 동일 created_at tie, 여러 상품의 한 그룹, 취소된 최신 → 이전 유효 주문, 삭제/영구삭제/테스트/다른 방송 제외, 자정·방송 종료, 모호한 닉네임 중단, 주문 없음, 주문 ID 소유자 불일치.
- 경품 저장: 수량1/0원/옵션없음, 주소·그룹·상태 유지, 총액/배송비/카드/계좌/기존 포인트 변화0, 재고 차감0, 새 줄 picked_at NULL, 기존 챙김 완료 그룹이 안 챙김으로 반영.
- 중복: 같은 winnerId 2/20 동시 요청 → 줄1/receipt1, 응답 유실 후 재시도, 두 실제 관리자 컴포넌트 mount, reconnect·reload·탭변경, 같은 고객의 서로 다른 당첨 → 각각1개.
- 다중 당첨: 1/여러명, 일부 소유자 오류, 각 사람의 최신 주문, 성공 건 재실행0, 실패 건 재시도 가능.
- 추첨 확정: 같은 eventId 동시 resolve/spin 결과·당첨 행 동일, 확정 저장 실패/당첨 행 실패 rollback, test/preview 주문·포인트 변화0.
- 금융: 지급 API 4xx/5xx/JSON 오류/네트워크 timeout, 이력 실패, 잔액 실패, receipt/완료 마킹 실패, 같은 source_key 병렬1회, 다른 source_key 같은 고객 합산, 차감 잔액 부족 rollback, 최초 balance 동시 생성, 기존 주문 포인트 사용/적립/복구와 교차 실행.
- 노출: 고객 조회, 관리자 목록·상세, 상품별/고객별 챙김, 결제완료 필터, 주문 엑셀, 구매 통계·응모권에서 경품을 유료 구매로 가산하지 않음.
- 회귀: 전체 scripts/test-*.mjs, guard, typecheck, production build, production 읽기 전용 smoke, 독립 최종 review.

실제 DB 병렬 검사는 운영과 동일 함수·제약조건을 설치한 격리 PostgreSQL/Supabase 환경에서 두 개 이상의 연결로 수행한다. 단일 연결 BEGIN/ROLLBACK은 rollback 검사만 증명하며 동시성 증거로 사용하지 않는다. 환경이 확보되지 않으면 해당 검사를 미실행이라고 남기고 안전 검수 완료로 배포하지 않는다.

## 10. 배포와 되돌리기

격리 검증 → 권한/advisors → 확정 migration → 운영 migration 적용 → 기능 flag OFF 상태에서 구버전 호환 확인 → 앱 배포 → 관리자 읽기 전용 확인 → 신규 실행 활성 순서. DB 실패를 앱 fallback 직접 INSERT로 우회하지 않는다.

운영 실고객 추첨/지급을 smoke 목적으로 실행하지 않는다. 새 경품 연결 데이터는 rollback 후에도 유지한다. 앱을 이전 커밋으로 되돌리더라도 보상 receipt/기록과 0원 상품 줄을 삭제하지 않는다. 자동 소급 지급/기존 고객 잔액 보정은 범위 밖이다.

## 12. 검토 결과

미확정 값·빈 설계 항목 없음. 사용자 승인한 최신 비취소 주문, 1개/0원/옵션없음, 방송 범위, test 무변경 기준을 유지했다.
선택 B의 비용은 DB migration과 서버 트랜잭션·실제 병렬 환경 검수가 필요하다는 점이다. 빠른 브라우저 INSERT 우회는 선택하지 않는다.
사용자의 문서 이후 진행 요청을 받아 구현 계획을 작성한다. 아직 기능 구현·운영 DB 변경은 하지 않았다. 금융 관련 내용은 검증만 포함하며 발견된 기존 포인트 결함 수정은 별도 승인 범위이다.
