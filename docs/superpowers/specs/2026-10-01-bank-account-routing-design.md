# 회원 유형별 입금계좌 노출 설계서

- 작성일: 2026-10-01
- 대상 서비스: 루루동이 집구석LIVE
- 상태: 사용자 승인 설계를 바탕으로 작성
- 목적: 기존 계좌를 유지하면서 계좌 1개를 추가하고, 관리자가 선택한 방식과 선택적 신규회원 유지기간에 따라 방송·쇼핑몰 주문 모두에 정확히 1개 계좌를 노출한다.

## 1. 현재 구조에서 확인한 사실

현재 배포된 관리자 및 고객 화면과 배포 코드를 읽기 전용으로 확인했다.

- 관리자 설정에는 은행·계좌번호·예금주로 구성된 계좌 1개만 존재한다.
- 기존 설정값은 `settings` 저장소의 단일 계좌 키로 저장된다.
- 고객 화면은 공통 상점 설정에서 현재 계좌를 읽어 주문완료와 주문조회 화면에 표시한다.
- 주문 제출은 `/api/customer-orders/submit` 서버 경로를 사용한다.
- 고객 연결에는 카카오 ID를 우선 사용하고 전화번호를 보조 식별자로 사용한다.
- 주문 상품들은 `orders`에 여러 행으로 저장되며 같은 주문서는 `order_group_id`로 묶인다.
- 삭제·취소·환불·테스트 주문을 구분할 수 있는 주문 상태와 플래그가 존재한다.
- 자동입금 확인은 뱅크다 연동과 별도이므로, 사이트에 계좌를 추가하는 것만으로 새 계좌의 자동입금 확인이 보장되지는 않는다.

## 2. 확정 요구사항

### 2.1 계좌 등록

- 기존 계좌는 그대로 `계좌 1`로 유지한다.
- 관리자가 `+ 계좌 추가`를 눌러 `계좌 2`를 한 개 더 등록할 수 있다.
- 등록 가능한 계좌는 최대 2개다.
- 각 계좌는 다음 값을 갖는다.
  - 내부 식별자
  - 관리자용 구분명
  - 은행
  - 계좌번호
  - 예금주
  - 사용 여부
- 계좌 2는 노출 규칙에서 사용 중이지 않을 때만 삭제할 수 있다.

### 2.2 노출 방식

관리자가 다음 두 방식 중 하나를 선택한다.

#### 전체 고객에게 같은 계좌

- `전체 고객에게 보여줄 계좌`에서 계좌 1 또는 계좌 2 중 정확히 하나를 선택한다.
- 이전 주문 이력 여부와 관계없이 선택한 계좌 하나만 노출한다.

#### 회원 유형별로 계좌 분리

- `기존회원에게 보여줄 계좌`에서 정확히 하나를 선택한다.
- `첫 주문 신규회원에게 보여줄 계좌`에서 정확히 하나를 선택한다.
- 두 항목에 같은 계좌를 선택할 수 있다.
- 두 항목에 서로 다른 계좌를 선택할 수 있다.

전체 고객 방식과 회원 유형별 방식은 동시에 활성화할 수 없다. 이로써 우선순위 충돌을 원천 차단한다.

### 2.3 신규회원 계좌 유지기간

- 회원 유형별 방식에서만 `신규회원 계좌 유지기간`을 선택적으로 켤 수 있다.
- 관리자는 시작일과 종료일을 한국 시간(KST) 날짜로 지정한다. 시작일 00:00:00부터 종료일 23:59:59.999까지를 포함한다.
- 지정 기간 안에 생애 첫 유효 주문을 제출한 고객은 그 기간이 끝날 때까지 다른 방송 또는 쇼핑몰에서 추가 주문해도 `first_order` 유형을 유지한다.
- 기간 시작 전에 유효 주문이 있었던 고객은 유지기간 대상이 아니며 기존회원이다.
- 기간이 끝난 뒤 새로 제출하는 주문부터는 정상 이력 판정에 따라 기존회원이 된다.
- 유지기간을 끄거나 날짜를 변경하면 저장 완료 뒤 제출되는 주문부터 즉시 새 기간으로 다시 판정한다.
- 과거 주문과 이미 저장된 주문의 계좌 사본은 기간 변경으로 수정하지 않는다.

### 2.4 방송 주문과 쇼핑몰 주문

- 방송 주문과 쇼핑몰 주문은 별도 계좌 정책으로 나누지 않는다.
- 쇼핑몰 주문도 전체 고객 방식, 회원 유형별 방식, 신규회원 유지기간을 방송 주문과 동일하게 적용한다.
- `broadcast_id`가 없는 쇼핑몰 주문끼리는 하나의 영구적인 같은 방송으로 묶지 않는다.

## 3. 회원 유형 판정

### 3.1 판정 기준

- `첫 주문 신규회원`: 현재 주문을 저장하기 직전까지 유효한 이전 주문 그룹이 0개인 고객
- `기존회원`: 유효한 이전 주문 그룹이 1개 이상인 고객
- 상품 행 수가 아니라 `order_group_id` 단위로 판정한다.
- 다음 주문은 이전 주문 이력에서 제외한다.
  - `is_deleted = true`
  - 테스트 주문
  - 주문취소 상태
  - 환불 상태
- 입금대기 상태라도 취소되지 않은 실제 주문은 주문 이력으로 인정한다. 다만 첫 주문이 활성 신규회원 유지기간 안에 있으면 기간 종료 전 추가 주문도 `first_order` 유형을 유지한다.

### 3.2 배정 우선순위

새 주문은 다음 순서로 판정한다.

1. 같은 `order_group_id`의 중복 제출이면 최초 저장된 유형과 계좌 사본을 그대로 반환한다.
2. 같은 값이 있는 `broadcast_id`에서 이미 유효 주문을 제출했다면 자정 경과·기간 변경·노출 방식 변경과 관계없이 그 방송에 최초 저장된 유형과 계좌 사본을 유지한다.
3. 현재 설정이 회원 유형별 방식이고 고객의 생애 첫 유효 주문 시각이 현재 활성 유지기간 안에 있으며 현재 주문 시각도 그 기간 안이면 `first_order`로 판정한다.
4. 위 조건이 아니면 이전 유효 주문 그룹이 0개일 때 `first_order`, 1개 이상일 때 `existing`으로 판정한다.
5. 현재 노출 방식에 맞는 계좌 하나를 선택하고 주문에 사본으로 저장한다.

같은 방송 유지 규칙은 사용자가 앞서 확정한 주문 일관성 규칙이므로 설정 즉시 적용의 예외다. 새 방송이나 쇼핑몰의 새 주문에는 최신 설정이 즉시 적용된다.

### 3.3 고객 식별

- 카카오 ID가 있으면 카카오 ID를 우선 식별자로 사용한다.
- 과거 주문에 카카오 ID가 없거나 고객 연결 이전 데이터이면 정규화된 전화번호를 보조 식별자로 사용한다.
- 하이픈 유무가 다른 같은 전화번호는 동일 고객으로 취급한다.
- 닉네임만으로는 회원 유형을 판정하지 않는다.

### 3.4 동시 주문 방지

같은 고객이 브라우저 두 개에서 거의 동시에 첫 주문을 제출하면 양쪽이 모두 신규회원으로 판정될 수 있다. 이를 막기 위해 회원 유형 판정과 주문 저장을 하나의 데이터베이스 트랜잭션으로 처리한다.

- 카카오 ID 또는 정규화 전화번호로 고객 잠금을 획득한다.
- 잠금 안에서 이전 주문 이력을 다시 조회한다.
- 회원 유형과 노출 계좌를 결정한다.
- 선택된 계좌의 사본을 주문에 저장한다.
- 주문 상품 행 전체를 저장한다.
- 어느 한 단계라도 실패하면 주문 전체를 저장하지 않는다.

## 4. 데이터 설계

### 4.1 계좌 설정

기존 `settings` 저장 방식을 유지하되, 계좌 목록과 노출 규칙을 버전이 있는 하나의 구조화된 설정으로 저장한다.

```json
{
  "version": 1,
  "accounts": [
    {
      "id": "primary",
      "label": "계좌 1",
      "bankName": "은행명",
      "accountNumber": "계좌번호",
      "holder": "예금주",
      "enabled": true
    },
    {
      "id": "secondary",
      "label": "계좌 2",
      "bankName": "은행명",
      "accountNumber": "계좌번호",
      "holder": "예금주",
      "enabled": true
    }
  ],
  "routing": {
    "mode": "split",
    "allAccountId": "primary",
    "existingAccountId": "primary",
    "firstOrderAccountId": "secondary",
    "firstOrderWindow": {
      "enabled": true,
      "startDate": "2026-10-01",
      "endDate": "2026-10-07"
    }
  }
}
```

- `mode`는 `all` 또는 `split`만 허용한다.
- `all`에서는 `allAccountId`만 사용한다.
- `split`에서는 `existingAccountId`와 `firstOrderAccountId`를 사용한다.
- `firstOrderWindow`는 `split`에서만 판정에 사용하며, 날짜는 `YYYY-MM-DD` 형식의 유효한 KST 날짜여야 한다.
- 시작일은 종료일보다 늦을 수 없다.
- 선택된 계좌는 반드시 존재하고 `enabled = true`여야 한다.
- 계좌번호는 표시용 원본과 비교용 숫자 정규화 값을 구분한다.

### 4.2 주문별 계좌 사본

설정 변경이 과거 주문에 영향을 주지 않도록 `orders`의 각 주문 상품 행에 다음 값을 저장한다.

- `customer_order_segment`: `first_order` 또는 `existing`
- `payment_bank_account_id`
- `payment_bank_name`
- `payment_bank_account`
- `payment_bank_holder`
- `payment_bank_assigned_at`

같은 `order_group_id`의 모든 행에는 동일한 계좌 사본이 저장되어야 한다. 고객 화면은 현재 상점 설정이 아니라 주문에 저장된 계좌 사본을 우선 표시한다.

### 4.3 기존 데이터 호환

- 배포 시 현재 단일 계좌를 자동으로 `계좌 1(primary)`로 변환한다.
- 초기 노출 방식은 `전체 고객에게 같은 계좌`로 설정한다.
- 초기 전체 고객용 계좌는 기존 계좌 1로 지정한다.
- 기존 주문에는 계좌 사본이 없으므로 기존 동작과 동일하게 현재 계좌 1을 표시한다.
- 새 기능 저장이 완료되기 전까지 기존 단일 계좌 설정 키를 읽는 호환 코드를 유지한다.
- 안정화 기간 후에만 기존 키 제거를 별도 작업으로 진행한다.

## 5. 관리자 화면 설계

### 5.1 계좌 카드

`설정 → 상점 정보 → 무통장 입금계좌` 영역을 다음 순서로 구성한다.

1. 계좌 1 카드
2. 계좌 2 카드 또는 `+ 계좌 추가` 버튼
3. 고객별 노출 설정
4. 손님 화면 미리보기
5. 저장 버튼

각 계좌 카드에는 구분명·은행·계좌번호·예금주·사용 여부를 표시한다. 계좌번호는 편집하지 않을 때 일부를 가려서 표시한다.

### 5.2 노출 설정 UI

- 라디오 버튼
  - `전체 고객에게 같은 계좌`
  - `회원 유형별로 계좌 분리`
- 전체 고객 방식 선택 시
  - `전체 고객 계좌` 선택 상자 1개
- 회원 유형별 방식 선택 시
  - `기존회원 계좌` 선택 상자 1개
  - `첫 주문 신규회원 계좌` 선택 상자 1개
  - `신규회원 계좌 유지기간 사용` 스위치
  - 사용 시 시작일·종료일 입력
- 선택 상자에는 사용 중인 계좌만 표시한다.
- 미리보기에는 기존회원·첫 주문 신규회원·유지기간 대상 신규회원에게 실제로 표시될 계좌와 적용 기간을 보여준다.
- 별도의 쇼핑몰 계좌 선택란은 만들지 않고 `방송·쇼핑몰 공통 적용`임을 명시한다.

### 5.3 저장 검증

다음 조건에서는 저장하지 않는다.

- 은행·계좌번호·예금주 중 하나라도 비어 있음
- 계좌번호가 허용 형식이 아님
- 노출 규칙이 사용 중지된 계좌를 가리킴
- 회원 유형별 방식에서 기존회원 또는 신규회원 계좌가 선택되지 않음
- 전체 고객 방식에서 전체 고객 계좌가 선택되지 않음
- 노출 규칙에서 사용 중인 계좌 2를 삭제하려고 함
- 유지기간 시작일 또는 종료일이 비어 있거나 실제 달력에 없는 날짜임
- 유지기간 시작일이 종료일보다 늦음

계좌번호 또는 예금주가 바뀌면 저장 전에 변경 전·후를 보여주는 확인창과 뱅크다 확인 경고를 표시한다.

## 6. 서버 및 API 설계

### 6.1 관리자 설정 API

현재 `/api/admin-live/shop-info`를 확장한다.

- `GET`
  - 기존 상점 정보
  - 계좌 1·계좌 2
  - 노출 방식과 계좌 선택값
  - 기존 설정을 새 형식으로 변환한 결과
- `POST`
  - 관리자 인증 확인
  - 서버에서 전체 설정 재검증
  - 한 번의 저장으로 계좌 목록과 노출 규칙을 함께 반영
  - 저장 실패 시 기존 설정 유지
  - 저장 성공 직후 이후 주문이 최신 설정을 읽도록 별도 장기 캐시를 두지 않음

### 6.2 주문 제출 API

`/api/customer-orders/submit`에서 다음을 서버가 결정한다.

1. 고객 식별자 정규화
2. 동일 주문 재시도와 같은 방송의 기존 배정 조회
3. 첫 유효 주문 시각과 현재 활성 유지기간 조회
4. 확정 우선순위로 `first_order` 또는 `existing` 판정
5. 현재 노출 설정에 따라 계좌 1개 선택
6. 선택 계좌의 사본을 주문 행에 저장
7. 주문완료 응답에 선택된 계좌 사본 반환

클라이언트가 회원 유형이나 계좌 ID를 보내더라도 신뢰하지 않는다. 계좌 선택은 반드시 서버 판정만 사용한다.

### 6.3 설정 즉시 적용과 원자성

- 계좌 목록·노출 방식·유지기간은 하나의 버전 설정 JSON으로 한 번에 저장한다.
- 주문 트랜잭션은 시작 시점에 최신 커밋 설정 한 벌을 읽는다. 저장 도중 설정이 바뀌어도 일부는 이전값, 일부는 새값인 혼합 설정을 사용하지 않는다.
- 관리자 저장이 완료된 뒤 시작된 새 주문에는 변경한 날짜·방식·계좌 선택을 즉시 적용한다.
- 설정 저장과 주문 제출이 정확히 동시에 발생하면 주문은 완전한 이전 설정 또는 완전한 새 설정 중 하나만 사용한다.
- 이미 저장된 주문, 중복 재시도, 같은 방송에서 유지되는 계좌 사본은 설정 변경으로 덮어쓰지 않는다.

### 6.4 고객 주문조회

- 주문 그룹별 계좌 사본을 반환한다.
- 주문조회에서 `입금 계좌 보기`를 누르면 해당 주문에 저장된 계좌를 표시한다.
- 과거 주문처럼 사본이 없으면 기존 계좌 1로 대체한다.
- 서로 다른 날짜의 주문이 서로 다른 계좌를 사용했더라도 각각 올바른 계좌가 표시되어야 한다.

## 7. 오류 처리 원칙

- 유효한 계좌를 결정하지 못하면 주문을 저장하지 않고 고객에게 `입금계좌 설정을 확인 중입니다. 잠시 후 다시 주문해 주세요.`라고 안내한다.
- 잘못된 계좌로 주문을 접수하는 것보다 주문을 중단하는 것을 우선한다.
- 여러 상품 행 중 일부만 저장되는 부분 저장을 허용하지 않는다.
- 설정 저장 실패 시 화면의 입력값과 서버 저장값을 구분해서 안내한다.
- 계좌번호 전체를 콘솔 로그·분석 이벤트·오류 추적 도구에 남기지 않는다.
- 관리자 로그에는 계좌 내부 ID와 변경 주체·시간만 기록하고 전체 계좌번호는 기록하지 않는다.

## 8. 뱅크다 자동입금 확인

- 사이트 계좌 노출과 뱅크다 등록 계좌는 서로 다른 설정이다.
- 계좌 2를 노출하기 전에 뱅크다에도 해당 계좌가 등록되어 있는지 관리자가 확인해야 한다.
- 현재 뱅크다 연동이 계좌 2개를 동시에 조회하는지는 별도 연동 설정을 확인해야 한다.
- 확인되지 않은 상태에서 `자동입금 가능`으로 표시하지 않는다.
- 계좌별 자동입금 지원 상태를 확인할 수 없다면 관리자 화면에 `뱅크다 등록 여부를 직접 확인하세요`라는 경고만 표시한다.

## 9. 필수 테스트

### 9.1 설정 테스트

- 기존 계좌만 있는 상태에서 기존 화면과 동일하게 동작
- 계좌 2 추가·수정·삭제
- 전체 고객 방식에서 계좌 1 선택
- 전체 고객 방식에서 계좌 2 선택
- 회원 유형별 방식에서 서로 다른 계좌 선택
- 회원 유형별 방식에서 같은 계좌 선택
- 사용 중인 계좌 삭제 차단
- 필수값 누락 및 잘못된 계좌번호 차단
- 저장 실패 시 기존 설정 보존

### 9.2 회원 판정 테스트

- 주문 이력 0건 → 첫 주문 신규회원
- 유효 주문 그룹 1건 이상 → 기존회원
- 주문 상품 행이 여러 개여도 주문 그룹 1건으로 계산
- 삭제 주문만 존재 → 첫 주문 신규회원
- 취소 주문만 존재 → 첫 주문 신규회원
- 환불 주문만 존재 → 첫 주문 신규회원
- 테스트 주문만 존재 → 첫 주문 신규회원
- 입금대기 중인 정상 주문 존재 → 기존회원
- 카카오 ID는 같고 전화번호 형식이 달라도 기존회원
- 과거 카카오 ID가 없는 주문과 동일 전화번호 → 기존회원
- 닉네임만 같은 다른 전화번호 → 서로 다른 고객

### 9.3 주문·화면 테스트

- 전체 고객 방식에서 신규·기존 모두 선택 계좌 1개만 표시
- 분리 방식에서 신규회원에게 신규회원용 계좌만 표시
- 분리 방식에서 기존회원에게 기존회원용 계좌만 표시
- 주문완료 화면의 계좌와 주문조회 계좌가 동일
- 계좌번호 복사 값이 화면 표시 계좌와 동일
- 계좌 설정 변경 후에도 이전 주문에는 당시 계좌가 표시
- 설정 변경 후 새 주문에만 새 계좌 적용
- 기존 주문 사본이 없는 경우 계좌 1로 호환 표시
- 카드결제 주문에는 불필요한 입금계좌 안내가 노출되지 않음
- 쇼핑몰 주문도 방송 주문과 같은 전체/분리/유지기간 규칙 적용
- 유지기간 중 첫 주문 고객이 다른 방송 및 쇼핑몰에서 추가 주문해도 신규회원 계좌 유지
- 유지기간 종료 후 새 주문은 기존회원 계좌로 전환
- 유지기간 날짜·노출 방식을 변경한 직후 새 방송/쇼핑몰 주문에 최신 설정 적용
- 같은 방송의 추가 주문은 자정 경과·유지기간 종료·설정 변경 후에도 최초 계좌 사본 유지
- 고객 계좌 영역에 `입금 계좌는 변경될 수 있습니다. 입금 전 이 화면의 계좌번호를 꼭 확인해 주세요.` 표시

### 9.4 장애·경합 테스트

- 같은 고객이 동시에 첫 주문 2건 제출
- 주문 저장 도중 네트워크 중단
- 계좌 설정이 잘못된 상태에서 주문 제출
- 계좌 2를 비활성화하는 순간 주문 제출
- 유지기간 또는 노출 방식을 저장하는 순간 주문 제출(완전한 이전/새 설정 중 하나만 사용)
- 유지기간 경계 시각(KST 시작일 00:00, 종료일 23:59:59.999, 다음 날 00:00)
- 주문 상품 행 일부 저장 실패
- 서버 재시도 및 중복 제출
- 데이터베이스 마이그레이션 전·중·후 기존 주문조회

## 10. 배포 및 롤백

1. 기존 계좌 설정과 주문 테이블 백업
2. 주문 계좌 사본 컬럼과 서버 트랜잭션 추가
3. 기존 단일 계좌를 계좌 1로 자동 변환
4. 관리자 계좌 2 및 노출 설정 UI 배포
5. 고객 화면은 계좌 사본 우선·기존값 대체 방식으로 배포
6. 테스트 계정으로 신규회원·기존회원 주문 각각 1건 검증
7. 뱅크다 자동입금 대상 계좌 확인
8. 이상이 없을 때 기능 활성화

롤백 시에는 노출 방식을 전체 고객·계좌 1로 되돌리고, 기존 단일 계좌 키를 계속 읽도록 한다. 새 주문 컬럼은 데이터 손실 방지를 위해 즉시 삭제하지 않는다.

## 11. 완료 기준

- 관리자가 기존 계좌 외에 계좌 1개를 추가할 수 있다.
- 관리자가 전체 고객용 계좌 하나를 선택할 수 있다.
- 또는 기존회원용·첫 주문 신규회원용 계좌를 각각 하나씩 선택할 수 있다.
- 선택한 기간에 첫 주문한 회원이 기간 종료까지 방송·쇼핑몰 추가 주문에서도 신규회원용 계좌를 유지한다.
- 기간·노출 방식 변경은 저장 직후 새 주문부터 적용되며 혼합 설정이 발생하지 않는다.
- 쇼핑몰 주문은 방송 주문과 동일한 규칙을 사용한다.
- 고객에게 조건에 맞는 계좌 하나만 노출된다.
- 서버가 회원 유형과 계좌를 결정하며 클라이언트 조작으로 바꿀 수 없다.
- 과거 주문의 계좌가 설정 변경으로 바뀌지 않는다.
- 취소·삭제·환불·테스트 주문 때문에 기존회원으로 잘못 판정되지 않는다.
- 동시 주문에서도 신규회원 판정이 중복되지 않는다.
- 주문완료·주문조회·계좌 복사 값이 모두 동일하다.
- 전체 테스트 항목과 운영 화면 수동 검수가 통과한다.

## 12. 구현 전제

현재 배포 소스의 `origin/main`에서 분리한 전용 작업 브랜치와 워크트리에서 구현한다. 원래 체크아웃의 사용자 파일과 미추적 파일은 수정하지 않는다. 운영 데이터베이스 적용과 배포 전에는 자동 테스트·빌드·브라우저 검수 및 마이그레이션 사전 검증을 완료한다.
